# 004 — 미션 CRUD API

## 받은 티켓 스펙 요약

- scope: `app/api/missions/**`, `entities/mission/model/**`
- 필드 매핑: `topic↔category`, `todo↔title`, `deadline↔deadline`,
  `isImportant↔urgent`, `isCompleted↔done`,
  `actualFocusMinutes`는 DB 컬럼 없음 → `focus_sessions.duration_min` 합산으로 계산
- `GET /api/missions`: missions ↔ focus_sessions left join, 응답은 `Mission[]` (배열 그대로)
- `POST /api/missions`: body `CreateMissionInput`, `user_id`는 DB 기본값(`auth.uid()`)
  자동 채움, 응답은 `Mission` (`actualFocusMinutes: 0`)
- `PATCH /api/missions/:id`: 부분 수정, 응답은 `Mission`
- `DELETE /api/missions/:id`: `focus_sessions`는 cascade로 자동 삭제
- 제약: `entities/mission/model/useAddMission.ts`(POST 호출부)는 수정 없이 그대로
  붙어야 함 → 응답 포맷을 그 훅의 기존 사용 방식에 맞출 것

## 변경한 파일 목록

- `src/app/api/missions/route.ts` — 데모 인메모리 스토어 대신 Supabase 조회/삽입으로 교체 (GET/POST)
- `src/app/api/missions/[id]/route.ts` — 신규 동적 라우트 (PATCH 부분 수정 / DELETE)
- `src/entities/mission/model/mapMissionRow.ts` — 신규. DB row → `Mission` 매핑 공통 헬퍼
  (`focus_sessions.duration_min` 합산 포함)
- `src/entities/mission/model/types.ts` — `UpdateMissionInput` 타입 추가 (PATCH body용)
- `src/entities/mission/model/useMissions.ts` — GET 응답이 `{ missions: [...] }` 래핑
  객체에서 `Mission[]` 배열 그대로 바뀐 스펙에 맞게 파싱 로직 수정
- `src/entities/mission/model/mapMissionRow.test.ts` — 신규. `toMission` 단위 테스트
  (필드 매핑, `focus_sessions.duration_min` 합산 0/1/N건, null/undefined 케이스)

## 실제로 붙인 흐름 (요청 스펙과 실제 코드의 차이점 확인)

- `entities/mission/model/useAddMission.ts`는 실제로는 존재하지 않고,
  POST 호출부는 `src/features/add-mission/model/useAddMission.ts`에 있음(스코프 밖).
  이 훅은 `response.json()`을 그대로 리턴만 하고 필드를 destructure하지 않으므로,
  POST 응답을 스펙대로 raw `Mission` 객체로 반환하면 훅 수정 없이 그대로 호환됨 — 확인 완료.
- `src/entities/mission/model/useMissions.ts`는 스코프 안이라 GET 응답 포맷
  변경(`{missions:[]}` → `Mission[]`)에 맞춰 함께 수정함.

## 블로커

1. ~~`npm run typecheck` / `npm run test` 스크립트 부재~~ — **해결됨.** `package.json`에
   `typecheck`(`next typegen && tsc --noEmit`)와 `test`(`vitest run`) 스크립트, `vitest`
   devDependency가 추가되어 `mapMissionRow.toMission`에 대한 단위 테스트
   (`mapMissionRow.test.ts`)를 작성·실행할 수 있었음. 다만 API 라우트(`route.ts`,
   `[id]/route.ts`) 자체에 대한 통합 테스트는 아직 없음 — Supabase 클라이언트를 모킹하는
   테스트 설정이 필요해 범위가 더 크고, Docker 없이는 로컬 Supabase로 실제 검증도
   어려워 이번 턴에는 단위 테스트만 추가함. 통합 테스트는 후속 작업으로 남김.
2. **`features/toggle-mission/model/useToggleMission.ts`와의 계약 불일치**: 이 훅은
   현재 `PATCH /api/missions` (컬렉션 경로, body에 `{id, isCompleted}`)를 호출하는데,
   이번 티켓 스펙은 `PATCH /api/missions/:id`(동적 세그먼트)만 정의함. 컬렉션
   경로(`/api/missions`)에는 PATCH 핸들러를 두지 않았으므로, 이 훅을 수정하지 않는 한
   토글 기능이 405로 깨짐. `features/toggle-mission/**`는 스코프 밖이라 직접 수정하지
   않았음 — 별도 티켓에서 이 훅을 `PATCH /api/missions/${id}` 형태로 옮겨야 함.
3. **`deadline` 컬럼 타입(`timestamptz`)과 프런트 입력값(`"13:00"` 등 시각 문자열) 간
   포맷 불일치 가능성**: 스펙이 `deadline↔deadline` 1:1 매핑을 명시했고 스키마는
   이미 확정된 아키텍처 결정이라 그대로 pass-through만 구현함. `AddMissionModal`이
   `"13:00"`처럼 날짜 없는 시각 문자열을 보내면 Postgres가 `timestamptz` 캐스팅에
   실패할 수 있음 — 이 티켓 스코프 밖의 스키마/폼 설계 이슈로 별도 확인 필요.
4. **기존 데모 인메모리 스토어(`shared/lib/demo-store.ts`)와의 이원화**: `checkins`,
   `nag` 라우트는 여전히 데모 스토어의 미션 데이터를 참조하는데, 이번 티켓으로
   `missions` API만 실제 Supabase로 옮겨져 두 데이터 소스가 분리됨. 스코프 밖이라
   손대지 않았으나, 추후 해당 라우트들도 Supabase로 이관하는 티켓이 필요함.
