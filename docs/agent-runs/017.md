# 017 — 쓴소리 날짜 경계 캐싱 버그 수정

## 받은 티켓 스펙 요약

- 브랜치: `ticket/017-nag-date-boundary-cache` (이미 생성된 상태에서 시작)
- scope: `src/app/api/nag/route.ts`, `supabase/migrations/**`(nag_logs 마이그레이션이 필요할 때만)
  - tickets/017.md 파일은 이 워크트리에 없어서, 사용자가 채팅으로 첨부한 티켓 원문을 스펙으로 취급함
- 증상: "10월 1일에 재생성을 누르지 않았다면 10월 2일에도 1일 전 쓴소리가 그대로 보임"
- 요구사항
  1. `nag_logs.context`에 앱 기준 오늘 날짜(`getAppToday()` 문자열)를 `date`로 저장. date가 없는 옛 레코드는
     "오늘 로그가 아님"으로 취급 (마이그레이션 없이 애플리케이션에서 처리)
  2. `canReuseCache`에 "저장된 date === 오늘" 조건 추가. 날짜가 다르면 mode/persona가 같아도 재생성
  3. 날짜 변경으로 재생성될 때 `regenerate_count`는 0 (기존 로직 확인만)
  4. 기존 테스트 파일에 "날짜가 바뀌면 mode가 같아도 재생성" 테스트 추가. **수정 전 코드에서 실패하는 것을 먼저 확인**

## 무슨 문제가 있었나 (원인 분석)

`GET /api/nag`의 흐름은 이렇다.

1. `collectNagAggregate`가 미션/집중/체크인을 모아 오늘의 `mode`("fail" | "success")를 계산
2. `fetchLatestNagLog`가 `nag_logs`에서 `generated_at` 내림차순으로 **가장 최근 1건**을 가져옴
3. `resolveNagMessage`가 아래 조건을 만족하면 OpenAI를 호출하지 않고 저장된 문구를 그대로 돌려줌

```ts
const canReuseCache =
  !options.forceRegenerate && latestLog !== null && storedPersonaId !== undefined && storedMode === aggregate.mode;
```

이 조건에는 **"그 로그가 언제 만들어졌는지"가 전혀 들어 있지 않다**. 캐시 키가 사실상 `(persona, mode)` 두 개뿐이었다.

그래서 이런 일이 생긴다.

| 시점 | 상황 | 결과 |
| --- | --- | --- |
| 10/1 | 미션 미완료 → mode "fail", 문구 A 생성·저장 | 정상 |
| 10/2 아침 | 새 날이지만 아직 미션을 하나도 안 끝냄 → mode 또 "fail" | 최신 로그(10/1의 A)와 mode·persona가 같아서 **A를 그대로 재사용** |
| 10/3, 10/4 … | 계속 fail이면 | 사용자가 "한 번 더 때려줘"(POST)를 누르기 전까지 **A가 영원히 노출** |

특히 이 앱은 하루를 시작할 때 거의 항상 "미완료 미션이 있음 = fail" 상태라서, 날짜가 바뀐 아침에는 mode가 바뀌지 않는 경우가
대부분이다. 즉 이 버그는 드문 경계 상황이 아니라 **매일 아침 거의 확실하게 재현되는** 버그였다. 또 쓴소리 프롬프트에는 그날의 완료율,
집중시간, 남은 미션 제목이 들어가므로, 전날 문구를 다시 보여주면 **이미 끝난(혹은 어제의) 미션 이름을 지적하는 틀린 메시지**가 된다.

## 고려한 방법들과 선택

### 결정 1. "오늘 로그인지"를 어떻게 판단할까

| 대안 | 설명 | 장점 | 단점 | 채택 |
| --- | --- | --- | --- | --- |
| (A) `context.date`에 앱 기준 날짜 문자열 저장 후 비교 | 저장 시 `getAppToday()` 값을 context에 넣고, 조회 시 문자열 비교 | 티켓 지시와 일치. 스키마 변경 없음. 앱의 "하루" 정의(KST 새벽 2시 경계)를 그대로 따름. 비교가 단순 문자열 `===` | date가 없는 옛 레코드 처리 필요 → 아래처럼 "오늘 아님"으로 취급하면 해결 | **채택** |
| (B) 기존 `generated_at` 컬럼으로 비교 | select에 `generated_at`을 추가하고 `getAppToday(new Date(generated_at)) === today`로 판단 | 옛 레코드도 날짜를 알 수 있음 | 티켓이 명시적으로 (A)를 지시함. 저장 시각(DB 기본값)과 앱 시각이 다른 출처라 경계 근처에서 어긋날 여지. context에 "어떤 하루를 위해 만든 문구인지"가 남지 않아 디버깅·재현용 기록(nag_logs의 목적)으로서 정보가 줄어듦 | 기각 |
| (C) 조회 쿼리 자체를 오늘 범위로 제한 | `fetchLatestNagLog`에 `.gte("generated_at", todayRange.start)` 추가 | 오늘 로그만 가져오니 캐시 판단이 자연스러움 | **POST의 regenerate_count 누적과 페르소나 유지가 깨짐**: 최신 로그를 못 가져오면 `storedPersonaId`가 사라져 날짜가 바뀐 첫 GET에서 페르소나가 기본값(첫 번째)으로 튀어버림. 사용자가 고른 페르소나는 날이 바뀌어도 유지돼야 함 | 기각 |
| (D) DB 마이그레이션으로 `nag_logs.app_date` 컬럼 추가 | 별도 컬럼 + 인덱스 | 쿼리 레벨 필터링 가능 | 티켓이 "마이그레이션 불필요"라고 명시. 여러 워크트리가 병렬로 돌아가는 상황에서 마이그레이션 추가는 충돌 위험만 늘림. 하루 1건 정도의 로그라 인덱스 이득도 없음 | 기각 |

(A)를 택하면서도 **최신 로그 1건을 가져오는 쿼리는 그대로 두었다**. 날짜가 달라 캐시를 못 쓰더라도 그 로그의 `personaId`는
"사용자가 마지막으로 고른 페르소나"로서 계속 쓰여야 하기 때문이다. 테스트에서도 "어제 로그의 persona가 realist면 오늘 재생성도 realist"를
검증한다.

### 결정 2. "오늘" 값을 어디서 계산할까

| 대안 | 설명 | 채택 |
| --- | --- | --- |
| (a) `resolveNagMessage`·`saveNagLog` 안에서 각각 `getAppToday()` 호출 | 가장 단순 | 기각 |
| (b) `collectNagAggregate`가 이미 쓰는 `now`로 한 번만 계산해 `aggregate.today`로 전달 | 집계·캐시 비교·저장이 모두 같은 시각 기준 | **채택** |

(a)는 한 요청 안에서 `new Date()`를 여러 번 부르게 된다. 요청이 하필 KST 01:59:59.9xx에 들어와 집계는 "10/1"로, 캐시 비교는
"10/2"로 계산되면, **10/1 데이터로 만든 문구에 10/2 날짜가 찍혀 저장**되고 그날 내내 캐시로 재사용되는 미세한 경계 버그가 생길 수 있다.
(b)는 `collectNagAggregate`가 이미 오늘 집중시간 범위를 구하려고 `getAppToday(now)`를 계산하고 있었으므로, 그 값을 `NagAggregate.today`로
노출만 하면 된다. 추가 비용이 없고 "이 문구는 이 날짜의 데이터로 만들었다"가 항상 일치한다.

### 결정 3. date가 없는(017 이전) 레코드 처리

| 대안 | 채택 |
| --- | --- |
| date가 없으면 예전처럼 mode만 보고 재사용 (하위 호환 우선) | 기각 — 버그가 배포 직후 그대로 남음. 바로 그 옛 로그가 문제의 "전날 문구"일 가능성이 높음 |
| date가 없으면 `generated_at`으로 추정 | 기각 — 결정 1의 (B)와 같은 이유, 코드 경로만 둘로 늘어남 |
| **date가 없으면 "오늘 아님" → 재생성** | **채택** — 티켓 지시 그대로. 비용은 배포 직후 사용자당 GET 1회분 OpenAI 호출뿐이고, 재생성된 로그에는 date가 채워지므로 다음 GET부터는 정상 캐시됨 |

구현은 `typeof context.date === "string"`일 때만 값을 쓰고 그 외(누락, null, 숫자 등 이상값)는 `undefined`로 보아
`storedDate === aggregate.today`가 항상 false가 되게 했다. 기존 `isNagPersonaId`/`isNagMode`처럼 DB의 jsonb를 신뢰하지 않는
같은 패턴을 따랐다.

### 결정 4. regenerate_count

기존 코드 `options.forceRegenerate ? prev + 1 : 0`을 확인했다. 날짜 변경으로 인한 재생성은 GET 경로(`forceRegenerate: false`)에서만
일어나므로 자동으로 0이 된다. 로직은 바꾸지 않고 주석만 추가했으며, 테스트에서 "어제 로그의 regenerate_count가 4여도 오늘 GET 재생성은
0으로 저장"을 검증한다.

### 추가한 테스트 (모두 `vi.setSystemTime`으로 시각 고정)

1. **date=오늘, mode 동일 → 캐시 재사용**: OpenAI 미호출, insert도 미호출
2. **date=어제, mode·persona 동일 → 재생성**: OpenAI 1회 호출, persona 유지(realist), insert payload가 정확히
   `{ content, context: { mode: "fail", personaId: "realist", date: "2026-10-02" }, regenerate_count: 0 }` (어제 count가 4였어도 0)
3. **date 없는 옛 레코드 → 재생성**: persona(furious-boss)는 유지
4. **앱 하루 경계(KST 새벽 2시)**: KST 10/2 01:59에는 아직 앱 기준 10/1이라 date="2026-10-01" 로그를 재사용, 02:00부터는 재생성.
   단순 자정(00:00) 기준으로 잘못 구현하면 이 테스트가 잡아낸다
5. **같은 날 GET 3회 → 생성 1회**: insert 결과를 다음 조회가 이어받도록 nag_logs를 흉내 내, 첫 GET만 생성하고 이후 2회는 캐시를 쓰는지
   확인 (회귀 방지)
