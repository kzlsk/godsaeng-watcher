## 변경한 파일 목록

### 신규

- `src/features/add-mission/model/toDeadlineIso.ts` — "HH:mm" 문자열 + 기준 날짜(`now`, 기본값
  `new Date()`)를 받아 로컬 타임존 기준으로 해당 날짜의 해당 시각을 만든 뒤 `toISOString()`으로
  변환하는 순수 함수. 정규식으로 "HH:mm" 형식만 허용(00~23시, 00~59분), 형식이 아니면 에러를 던짐.
  조합 결과가 `now`보다 과거면 `setDate(+1)`로 다음 날로 롤오버.
- `src/features/add-mission/model/toDeadlineIso.test.ts` — 단위 테스트 4개
  (기본 변환 / 과거 시각 롤오버 / `now` 생략 시 현재 날짜 사용 / 잘못된 형식 에러).
  `now` 생략 케이스는 `vi.useFakeTimers()` + `vi.setSystemTime`으로 시스템 시각을 고정해서
  검증(롤오버 로직이 생긴 뒤로는 실제 벽시계 시각에 따라 테스트 결과가 달라질 수 있어 플레이키해지는
  것을 막기 위함).

### 수정

- `src/features/add-mission/model/useAddMission.ts` — POST 요청 body 조립 시
  `{ ...input, deadline: toDeadlineIso(input.deadline) }`로 `deadline` 필드만 변환해서 전송하도록
  수정. `AddMissionModal.tsx`는 그대로 "HH:mm" 문자열을 상태로 들고 있고, API 호출 직전(mutationFn)에서만
  변환하도록 해서 UI 쪽 변경 없이 처리함.

## DoD 체크 결과

1. **"13:00" → 오늘 날짜 기준 ISO 변환** — `toDeadlineIso("13:00", now)`가 `now`의 연/월/일 +
   13:00:00.000을 로컬 타임존 기준 `Date`로 만든 뒤 `.toISOString()`으로 변환함을
   `toDeadlineIso.test.ts` 첫 번째 테스트에서 검증(결과를 다시 `new Date(iso)`로 파싱해 연/월/일/시/분이
   기대값과 일치하는지 확인).
2. **자정을 넘긴 시각("00:30") 처리 — 과거 시각이면 다음 날로 롤오버** — 최초 구현은 "now의 날짜를
   무조건 그대로 사용"이었는데, 사용자 피드백으로 의도를 수정함: `now` 날짜 + 입력 시각을 조합한 결과가
   `now` 시점보다 과거면(예: 23:50에 "00:30" 입력 → 오늘 00:30은 이미 지난 시각) 하루를 더해 다음 날로
   계산하도록 변경(`deadline.getTime() < now.getTime()`이면 `setDate(+1)`). `now`가 "당일 23:50"일 때
   `toDeadlineIso("00:30", now)`를 호출하면 다음 날 00:30이 나오는 것을 테스트로 검증. 반대로 `now`가
   "당일 09:00"이고 입력이 "13:00"(미래 시각)이면 롤오버 없이 같은 날짜가 유지되는 것도 별도 테스트로
   검증. UTC로 직렬화된 `toISOString()` 결과의 날짜 부분(예: KST 자정 근처면 UTC 날짜가 하루 당겨질 수
   있음)은 timestamptz의 정상적인 표현이라 문제 삼지 않음 — 이건 "인스턴트가 꼬이는 것"이 아니라 UTC
   표기 특성이라 별개임.
3. **실제 API 호출로 Postgres insert 확인 — 미완료, 블로커 아님(환경 제약)**:
   - 이 worktree엔 `.env.local`이 없음(AGENTS.md에 따라 워크트리 생성 시 수동 복사가 필요한데 아직 안 됨)
   - `supabase start`용 Docker Desktop도 이 샌드박스 환경에서 접근 불가
     (`failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`)
   - 위 두 가지 다 `features/add-mission/**` scope 밖이라 직접 해결하지 않음
   - 대신 코드 레벨로 확인한 내용: `supabase/migrations/20260915054513_initial_schema.sql:7`에서
     `missions.deadline`이 `timestamptz` 컬럼임을 확인했고, `src/app/api/missions/route.ts`의 POST
     핸들러가 `body.deadline`을 그대로 `.insert({ deadline: body.deadline, ... })`에 넘기는 것도 확인함
     (별도 파싱/검증 없음). 따라서 `toDeadlineIso`가 만드는 표준 ISO 8601 문자열
     (`YYYY-MM-DDTHH:mm:ss.sssZ`)이 그대로 PostgREST를 거쳐 `timestamptz`로 정상 insert될 것으로
     판단하지만, 실제 브라우저/API 호출을 통한 end-to-end 확인은 못 했음.
   - `.env.local` 세팅 및 로컬 Supabase 기동 후 실제 호출 검증은 사용자 쪽 환경에서 후속으로
     진행 필요.

  (레포 루트가 아님 — `src/app`이 있는 프로젝트라 미들웨어도 `src/` 안에 있어야 Next.js가 인식함).
  `updateSession(request)`을 호출해 그대로 반환하고, matcher는 Supabase 공식 가이드의 표준 정규식
  (`/((?!_next/static|_next/image|favicon.ico|.*\.(?:svg|png|jpg|jpeg|gif|webp)$).*)`)을 그대로 사용.
  `updateSession` 자체(인증 가드 로직, `AUTH_GUARD_ENABLED` 분기 등)는 이미
  `src/shared/lib/supabase/proxy.ts`에 구현돼 있던 것을 그대로 연결만 함 — 새 인증 로직을 작성하지
  않음.

### DoD 체크 결과

- `updateSession`이 모든 요청에서 호출되도록 연결 — `middleware.ts`의 `middleware()` 함수가
  `updateSession(request)`을 호출/반환하는 것으로 확인.
- 표준 matcher 적용 — Supabase 공식 가이드의 정규식을 그대로 사용, 별도 커스터마이징 없음.
- 실제 요청이 미들웨어를 타는지(브라우저/curl로 리다이렉트 등 확인)는 이 worktree에 `.env.local`/로컬
  Supabase가 없어 못 했음 — 기존 블로커와 동일 사유. `npm run typecheck`/`lint`/`test`는 모두 통과.

### 통합 게이트(npm run typecheck && npm run lint && npm run test) 실행 결과

- **`npm run typecheck`** → 통과.
- **`npm run lint`** → 에러/경고 없음.
- **`npm run test`** (`vitest run`) → 8 files / 35 tests 전부 통과 (미들웨어 자체엔 새 로직이 없어
  별도 테스트를 추가하지 않음 — `updateSession`의 로직 테스트가 필요하다면 이 또한
  `shared/lib/supabase/**` scope라 별도 판단 필요).
