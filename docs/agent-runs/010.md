# 010 — checkins / focus-sessions Supabase 연동

## 받은 티켓 스펙 요약

- scope: `app/api/checkins/**`, `app/api/focus-sessions/**`,
  `entities/checkin/**`, `entities/focus-session/**`
- `app/api/missions/route.ts`(004 티켓)와 같은 패턴으로 `shared/lib/demo-store.ts` 참조를

- focus-sessions:

  - `GET /api/focus-sessions/weekly`: 주간 총 집중시간 집계
- 004의 `topic/todo ↔ category/title` 매핑 방식과 동일하게, 기존 프런트 타입

  거기에 맞춰 매핑할 것
- DoD: checkins GET/POST 실연동(demo-store 제거) / focus-sessions POST가 실제 세션 기록 저장 /
  주간 집계가 실제 합계 반환 / 기존 훅(`useCheckins` 등)이 수정 없이 그대로 붙는지 확인

## 실제 코드와 대조해서 발견한 스펙-코드 불일치 (설계 판단 근거)

붙이기 전에 `entities/checkin/model/types.ts`, `entities/checkin/model/useDailyStats.ts`,
`entities/focus-session/model/*`, `widgets/MissionBoard.tsx`, `widgets/FocusTimerPanel.tsx`,
`features/checkin-today/**`, `features/start-focus-session/**`를 먼저 읽었고, 티켓 설명과
실제 프런트 계약이 다음과 같이 어긋나 있음을 확인함:

- `useDailyStats()`는 `/api/checkins`를 파라미터 없이 호출하고 `DailyStats`
  (`totalFocusMinutes`, `focusAheadMinutes`, `delayMinutesToday`, `delayMinutesWeek`)를
  기대함 — 티켓이 말한 "applications/problems 조회"와 다른 응답 형태.
- `useCheckinToday()`(POST 호출부)는 body로 `{ missionId, isCompleted }`를 보냄 — DB
  `checkins` 테이블의 `applications`/`problems`와 무관한, 미션 완료 토글에 가까운 호출.
- `useFocusSession()`은 "현재 활성 세션 하나"(`status: idle|running|paused`,
  `elapsedSeconds` 등)라는 뷰 모델을 기대하지만, `focus_sessions` 테이블은
  `started_at/ended_at` 세그먼트를 행 단위로 쌓는 구조라 "pause" 상태를 표현하는
  컬럼이 없음.

004의 지침("프런트 타입과 DB 컬럼명이 다를 수 있으니 기존 프런트 타입을 먼저 확인하고
거기에 맞출 것")을 그대로 적용해, **기존 훅의 요청/응답 계약을 깨지 않는 것**을
우선순위로 두고 아래처럼 설계함:

- `GET /api/checkins`(파라미터 없음 = `?date=today`와 동일)는 여전히 `DailyStats` 필수
  필드를 채워서 반환하되, `totalFocusMinutes`는 `focus_sessions`에서 실집계하고,
  같은 응답 객체에 실제 `checkins` 행(`applications`, `problems`, `date`)도 함께 얹어
  반환함 — `useDailyStats`는 구조적 타이핑상 초과 필드를 무시하므로 그대로 동작하고,
  티켓이 요구한 "applications/problems 조회"도 같은 엔드포인트로 충족됨.
- `POST /api/checkins`는 body에서 `applications`/`problems`가 **숫자로 존재할 때만**
  upsert payload에 포함시킴. 기존 `useCheckinToday`가 보내는 `{missionId, isCompleted}`는
  두 필드가 없으므로 `{date}`만 upsert되어 오늘 행을 생성하거나(최초 1회) 아무 것도
  바꾸지 않는 no-op update가 됨 — applications/problems를 실수로 0으로 덮어쓰지 않음.
- `POST /api/focus-sessions`는 기존 `action: start|pause|resume` 계약을 그대로 받아서
  내부적으로 `focus_sessions` 세그먼트 행을 insert/update함. "pause"는 열린(`ended_at
  is null`) 세그먼트를 닫아 `ended_at`/`duration_min`을 채우고, "start"/"resume"은
  (혹시 열려 있는 세그먼트가 있으면 먼저 닫고) 새 세그먼트를 insert함. `GET`은 오늘
  세그먼트들을 모아 `FocusSession` 뷰 모델로 합성해서 반환.
- `focusAheadMinutes`/`delayMinutesToday`/`delayMinutesWeek`는 스키마 어디에도 근거
  컬럼이 없고(미션 완료 시각 자체가 저장되지 않음), 계산하려면 `missions` 테이블
  deadline과의 비교 로직이 필요함 — 이번 티켓 scope(`entities/checkin/**`,
  `entities/focus-session/**`)를 벗어나는 설계 결정이라 판단해 **0으로 고정** 반환하고
  아래 블로커에 기록함(하드코딩된 데모 값 9/47/132를 실계산 없는 0으로 대체한 것도
  같은 이유).

## Postgres 집계 vs 애플리케이션 레벨 집계 (선택 근거)

Supabase JS(PostgREST)는 커스텀 Postgres 함수(RPC) 없이는 `sum()` 같은 집계를 셀렉트
절에서 바로 못 쓴다. 이 프로젝트에 이미 다른 도메인 로직용 RPC/DB 함수가 없고(마이그레이션에
`handle_new_user_nag_settings()` 트리거 함수 하나뿐), 유저 1인당 주간 `focus_sessions`
행 수도 많지 않을 것으로 판단해 **애플리케이션 레벨 집계**(행을 그대로 select 해서
JS `reduce`)를 선택함. RPC 함수를 새로 추가하는 방식은 스키마 변경(마이그레이션 추가)이
필요해 스코프(엔티티/라우트)를 벗어난다고 판단.

## 블로커

1. **`focusAheadMinutes` / `delayMinutesToday` / `delayMinutesWeek`에 대응하는 DB 컬럼이
   없음**: `missions` 테이블에 완료 시각(`completed_at` 등)이 저장되지 않아 "마감 대비
   지연/단축 시간"을 계산할 근거 데이터가 스키마에 없음. 계산하려면 (a) `missions`에
   완료 시각 컬럼 추가하는 마이그레이션, (b) `missions.deadline`과 비교하는 로직이
   필요한데 둘 다 `entities/checkin/**`/`entities/focus-session/**` 스코프 밖(스키마
   변경, `entities/mission` 도메인 로직)이라 직접 진행하지 않음. 이번 구현에서는 해당
   3개 필드를 `0`으로 고정 반환해 `MissionBoard`가 `NaN`을 렌더링하는 것만 방지함 —
   실제 값 계산은 별도 티켓 필요.
2. **`checkins` 테이블(`applications`/`problems`)과 `checkin-today` 피처의 목적 불일치**:
   `useCheckinToday`는 실제로는 미션 완료 토글 시 호출되며 지원서/문제풀이 개수를
   입력받는 UI가 아직 없음. 이번 티켓에서 만든 `POST /api/checkins`는 진짜 체크인
   기록(`{applications, problems}`)을 받을 수 있게 설계했지만, 이를 입력하는 프런트
   폼/UI는 없는 상태 — `features/checkin-today/**`, `widgets/**`는 스코프 밖이라
   손대지 않음. 후속 티켓에서 실제 지원서/문제풀이 입력 UI를 붙여야 함.
   → **[추가 변경](#추가-변경--usecheckintoday-제거--스트릭-or-조건-확장)에서 해결**:
   `useCheckinToday`/`features/checkin-today/**` 자체를 제거하고, 미션 완료만으로도
   스트릭이 인정되도록 스트릭 판정 로직을 확장함. 지원서/문제풀이 입력 UI 부재
   자체는 여전히 남아있는 별도 이슈.
3. **`focus_sessions`의 "pause" 상태 표현 한계**: 스키마에 세션당 컬럼은
   `started_at/ended_at/duration_min/completed`뿐이라 "일시정지"를 별도 상태로 저장하지
   않고, pause를 "현재 세그먼트를 닫는 것"으로 모델링함(재개하면 새 세그먼트 insert).
   같은 미션에 대해 여러 세그먼트를 시간순으로 합산해 `elapsedSeconds`를 복원하도록
   `toFocusSession`을 작성했으나, 다른 미션으로 전환 후 원래 미션으로 다시 돌아오는
   등의 복잡한 시나리오까지 검증하지는 않음(현재 프런트 UI 흐름상 발생하지 않는 케이스).
4. **`app/api/checkins/streak`는 티켓의 "필요하면" 조건부 요청에 대한 자체 판단으로
   추가함**: 소비하는 프런트 훅은 아직 없음 (`app/api/streak/route.ts`는 여전히
   demo-store 기반이며 `entities/streak/**`는 이번 티켓 scope 밖이라 그대로 둠). 실제
   스트릭 UI를 이 엔드포인트로 옮기는 작업은 `app/api/streak/**`/`entities/streak/**`를
   다루는 별도 티켓에서 진행해야 함.
   → **[추가 변경](#추가-변경--usecheckintoday-제거--스트릭-or-조건-확장)에서 부분 갱신**:
   `entities/streak/**`가 이번 세션의 후속 요청으로 scope에 들어와 스트릭 판정 로직
   자체는 이제 `entities/streak/model`이 소유함. 다만 `app/api/streak/route.ts`

   손대지 않았음 — UI에 반영하려면 그 라우트를 이 로직으로 교체하는 별도 작업 필요.

### 설계 판단

- `missions` 테이블에는 완료 "시각"을 저장하는 컬럼이 없음(`done` boolean만 있고
  `completed_at` 같은 컬럼 없음 — 010 최초 구현 때 남긴 블로커 1과 동일한 스키마 한계).
  "그날 완료된 미션"을 판별할 날짜 기준으로 쓸 수 있는 건 `deadline`(nullable)과
  `created_at`(항상 존재, `default now()`) 뿐인데, `deadline`은 비어 있을 수 있어
  기준으로 삼으면 날짜 없는 미션이 통째로 스트릭 계산에서 빠지는 문제가 생김.
  → **`created_at` 날짜를 "그날"의 기준으로 채택**. 항상 값이 있고, "오늘 할 일로
  추가해서 오늘 완료했다"는 일반적인 사용 흐름과도 맞음. (`deadline` 기준이 맞다고
  판단되면 후속 티켓에서 바꿔야 함 — 스키마상 근거가 명확하지 않아 확정하지 않음.)

## 추가 변경 2 — `/api/streak`를 실제 데이터로 연결

같은 브랜치에서 이어진 후속 요청. scope: `app/api/streak/**`, `entities/streak/**`.

### 받은 스펙 요약

- `GET /api/streak`가 `demo-store` 대신 `entities/streak`의 실제 스트릭 계산 로직을
  사용하도록 연결
- 실제 Supabase 데이터(`checkins` + `missions`) 기반으로 계산된 현재 스트릭을 반환
- 기존 응답 형태(프론트가 기대하는 필드)는 유지, `demo-store` 참조는 제거
- DoD: demo-store 참조 제거 / 실제 로그인 계정으로 미션 완료 시 스트릭 반영을
  브라우저에서 확인 / 기존 프론트 컴포넌트가 수정 없이 그대로 붙는지 확인

### 설계 판단

- `useStreak()`/`StreakBar.tsx`/`MissionBoard.tsx`가 실제로 읽는 필드는
  `StreakSummary`(`currentStreak`, `weeklyScore`, `weeklyScoreDelta`, `last7Days`)
  전부이므로, `/api/checkins/streak`처럼 `currentStreak`만 반환해서는 안 되고
  네 필드를 모두 실데이터 기반으로 채워야 함.
  - `currentStreak`, `last7Days`: [1차 추가 변경](#추가-변경--usecheckintoday-제거--스트릭-or-조건-확장)에서
    만든 "체크인된 날" OR 조건(`checkins.applications/problems>0` 또는 그날
    `missions.done=true` 존재, `created_at` 날짜 기준)을 그대로 재사용해서 계산.
  - `weeklyScore`/`weeklyScoreDelta`: 대응하는 DB 컬럼이 전혀 없음(010 최초 구현
    블로커 1과 같은 스키마 한계). 다만 이번엔 `focusAheadMinutes`/`delayMinutes*`처럼
    필요한 데이터 자체가 스코프 밖(마감 시각 비교)이 아니라, **이미 갖고 있는
    "체크인된 날" 데이터**만으로 정의 가능한 지표라서 0 고정 대신 실계산으로
    구현함: `weeklyScore = round(이번 주(월~일) 체크인된 날 수 / 7 * 100)`,
    `weeklyScoreDelta = 이번 주 점수 - 지난 주 점수`. 이 공식은 스펙에 명시된 게
    아니라 이번 세션에서 정의한 것이므로, "점수"의 실제 기획 의도와 다를 수 있음
    (블로커 7).
- `app/api/checkins/streak/route.ts`는 이번 티켓 scope 밖이라 손대지 않았고, 그 안의
  "체크인된 날 판정 + 병합" 로직을 그대로 복붙하는 대신 `entities/streak/model`에
  `resolveCheckedInDates`(신규)로 옮겨 공용화함 — `/api/streak`가 이 함수를 가져다
  쓰고, `/api/checkins/streak`의 인라인 구현은 그대로 남아있어 두 라우트 간에 로직이
  중복된 상태(블로커 8). `resolveCheckedInDates`는 체크인 조건 판정에
  `entities/checkin/model/checkinQualifies.ts`(`isQualifyingCheckin`)를 그대로
  재사용함 — FSD 레이어 규칙은 "entities → features → widgets → app" 단방향 규칙이라
  entities 레이어 안에서 슬라이스 간(entities/streak → entities/checkin) 참조는
  역방향이 아니라고 판단해 그대로 재사용함(파일 자체를 수정하진 않았으므로
  `entities/checkin/**` 스코프 밖 규칙도 지킴).
- "오늘"/"이번 주 시작일" 계산은 `entities/checkin/model/date.ts`,
  `entities/focus-session/model/dateRange.ts`에 거의 동일한 함수가 이미 있지만,
  일부러 재사용하지 않고 `entities/streak/model/date.ts`에 다시 작성함 — 사소한
  날짜 계산 하나 때문에 스트릭 도메인이 다른 두 엔티티에 의존하게 만들 정도의
  가치는 없다고 판단(이미 이 프로젝트에 동일 패턴의 소규모 중복이 있음).
