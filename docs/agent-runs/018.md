## 1) 중지 즉시 반영 — 낙관적 갱신

### 문제

`stop()` / `start()` / `resume()`이 전부 `onSuccess` 안에서만 `setStatus`를 호출했다.
응답이 올 때까지 `status`는 `"running"`이고, `useEffect`의 `setInterval`도 계속 돌아
숫자가 흘렀다. 사용자 입장에서는 "중지를 눌렀는데 5초 동안 안 멈춘다".

### 한 일

`applyOptimistic(nextStatus, nextAnchor)` 헬퍼를 만들어, `mutate` 호출 **전에** 로컬 상태를
먼저 바꾸고 **롤백 함수를 반환**하게 했다. 세 핸들러 모두 이 패턴을 쓰고,
`onError`에 그 롤백 함수를 그대로 연결한다.

- `stop()`: 클릭한 순간의 값으로 화면을 바로 얼린다 (`runningSinceMs: null`)
- `start()` / `resume()`: 즉시 `running`으로 바꾸고 그 시각을 기준점으로 잡는다
- `onSuccess`에서는 `settleFrom(data, …)`으로 서버가 돌려준 실제 값에 다시 맞춘다

### 검토한 대안

- **TanStack Query의 `onMutate` + `setQueryData`로 낙관적 갱신**: 채택하지 않음.
  이 위젯이 쓰는 상태는 "일시정지"를 포함하는데, 일시정지는 DB에 컬럼이 없는 순수 프론트
  상태라 `FocusSession` 캐시에 그대로 넣을 수가 없다(`pausedMarker.ts` 주석이 설명하는 설계).
  캐시에 억지로 넣으면 서버 모델과 프론트 모델이 섞인다. 컴포넌트 로컬 상태만 먼저 바꾸는
  쪽이 기존 설계와 어긋나지 않는다.
- **롤백 시 "실패를 기다린 동안 흐른 시간"을 빼기**: 하지 않음. 실패했다는 건 DB 세그먼트가
  여전히 열려 있다는 뜻이고, 서버는 나중에 `ended_at - started_at`으로 그 시간까지
  집중 시간으로 계산한다. 화면에서만 빼면 오히려 DB와 어긋난다. 그래서 롤백은 기준점을
  그대로(`previousAnchor`) 되돌려 계속 세게 둔다.
- **실패 시 사용자에게 에러 메시지 띄우기**: 하지 않음. 티켓은 롤백까지만 요구했고,
  "멈췄다가 다시 흐르기 시작한다"는 변화 자체가 피드백이 된다. 토스트/배너는 이 위젯에
  없는 UI라 새로 만들면 스코프를 넘는다. 필요하면 별도 티켓으로.

## 2) 탭 전환 드리프트 — 누적 → 재계산

### 문제

```ts
setInterval(() => setElapsedSeconds((value) => value + 1), 1000)
```

브라우저는 백그라운드 탭의 `setInterval`을 쓰로틀링한다(크롬은 1분 단위까지 늘림,
모바일은 앱 전환/화면 잠금 시 아예 멈춤). "틱 횟수"를 세는 방식이라 **틱을 놓친 만큼
화면이 뒤처진다.** 반면 서버(`closeSession`)는 `ended_at - started_at`으로 실제 시간을
기록한다 → DB는 맞고 화면만 느림.

### 한 일

"기준점 + 지금의 실제 차이"로 매번 다시 계산하는 방식으로 바꿨다.

```ts
export interface ElapsedAnchor {
  baseSeconds: number;          // 기준 시각까지 이미 쌓인 초
  runningSinceMs: number | null; // 기준 시각. 멈춰 있으면 null
}

export function computeElapsedSeconds(anchor, nowMs) { … }
```

`setInterval`은 이제 값을 더하지 않고 `nowMs`만 갱신한다 → 틱을 몇 번 놓쳤든 다음 갱신 때
실제 시계로 다시 계산되므로 값이 항상 맞는다. 틱이 쓰로틀링되면 **갱신 주기만 성겨지고
숫자는 틀리지 않는다.**

복귀 즉시 따라잡도록 이벤트도 걸었다 (다음 틱까지 최대 1초를 기다리지 않게):

- `visibilitychange` — 탭 전환 / 화면 잠금 복귀 (티켓이 지정한 것)
- `pageshow` — 모바일 사파리 bfcache 복귀. 이때 `visibilitychange`가 오지 않는 경우가 있다
- `focus` — 창 포커스 복귀

### 검토한 대안

- **`FocusSession`에 `startedAt`을 추가해 순수하게 계산**: 이게 가장 정확하다
  (네트워크 지연만큼의 오차도 없어진다). 하지만 `entities/focus-session/model/types.ts`와
  `mapFocusSessionRow.ts`를 고쳐야 해서 **scope 밖**이라 하지 않았다.
  현재 방식은 "응답을 받은 시각"을 기준점으로 삼으므로 응답 지연(수백 ms)만큼 적게
  세지만, stop 시 최종 값은 서버 값으로 덮어쓰므로 DB 기록에는 영향이 없다.
- **Web Worker / `Worker` 안에서 타이머 돌리기**: 쓰로틀링을 피하는 흔한 우회책이지만,
  재계산 방식이면 애초에 쓰로틀링돼도 값이 안 틀리므로 불필요하다. 복잡도만 늘어난다.
- **복귀 시 `focusSessionQueryKey`를 refetch해서 서버 값으로 맞추기**: 하지 않음.
  서버도 결국 같은 벽시계를 쓰므로 네트워크 왕복 없이 로컬 재계산만으로 같은 값이 나온다.
  탭 복귀마다 요청을 보내는 건 019(API 지연) 맥락에서도 반갑지 않다.

### 여기서 걸린 lint 문제 (두 번 되돌림)

처음에는 기존 코드처럼 **렌더 중에** 서버 세션을 로컬 상태로 옮기면서
`Date.now()`로 기준 시각을 잡았다 → `react-hooks/purity`
("Cannot call impure function during render") 에러.

그래서 그 동기화를 `useEffect`로 옮겼더니 이번엔 `react-hooks/set-state-in-effect`
("Calling setState synchronously within an effect can trigger cascading renders") 에러.
이 저장소의 eslint 설정은 React 컴파일러 규칙을 켜 두어서, **렌더 중 setState는 허용하지만
(기존 코드가 쓰던 패턴) 렌더 중 impure 호출과 effect 안의 동기 setState는 둘 다 막는다.**

최종 선택: **"지금"을 읽는 틱을 멈춰 있을 때도 계속 돌린다.**
그러면 `nowMs`가 항상 1초 안쪽으로 최신이라, 렌더 중 동기화 블록이 `Date.now()` 대신
`nowMs`를 기준 시각으로 쓸 수 있다 (= 렌더가 순수해짐). 기존의 "렌더 중 동기화" 구조도
그대로 유지된다.

- 트레이드오프: 타이머가 멈춰 있어도 1초에 한 번 리렌더한다. 패널 하나라 비용은 사실상 없다.
- 트레이드오프: 동기화 시 기준 시각이 최대 1초 과거일 수 있어 표시가 그만큼 앞설 수 있다.
  서버 값을 받을 때마다 초기화되므로 **오차가 누적되지는 않는다** (기존 방식은 무제한 누적).
- 검토했다 버린 안: 동기화 때는 기준점을 비워 두고 첫 틱(콜백이라 setState 허용)이 채우게 하기
  → 복귀 직후 1초간 숫자가 얼고, 기준점이 1초 늦게 잡혀 영구히 1초 모자란다. 더 나쁘다.

### 동기화 가드를 바꾼 것 (회귀 방지)

기존 가드는 `status === "paused" && pausedMarker !== null`이었다. 낙관적 갱신을 넣으면서
`resume`/`stop` 직후에는 **로컬 상태가 이미 running/idle로 바뀌었는데 마커는 아직 남아 있는**
구간이 생긴다. 이 구간에 서버 값이 들어오면 일시정지해 있던 시간이 다시 섞인다
(일시정지를 가로지르는 DB 세그먼트가 아직 열려 있기 때문).
그래서 가드를 `pausedMarker !== null` 하나로 바꿨다 — 애초에 "서버 값을 믿을 수 없는 조건"은
로컬 status가 아니라 마커의 존재 여부다.

## 3) 60분 이상 표시

`formatClock`이 60분 미만은 `MM:SS`, 60분 이상은 `H:MM:SS`를 쓰도록 수정했다.

- **항상 `H:MM:SS`로 통일**은 하지 않음. 평소(대부분의 세션)에 `0:02:54`가 되어
  쓸데없이 길어지고 디자인상 숫자 크기(39px)도 커 보인다. 시 자리는 실제로 넘겼을 때만 붙인다.
- `Math.max(0, Math.floor(…))`로 음수/소수를 먼저 정규화했다. 지금 호출부는 정수 초만
  넘기지만, `computeElapsedSeconds`가 시계 보정 같은 외부 요인에 노출돼 있어 방어해 둠.
- `tabular-nums`를 추가했다. 숫자 폭이 고정돼 매초 글자가 좌우로 흔들리지 않는다
  (`MM:SS` ↔ `H:MM:SS`로 자리수가 바뀔 때 특히 티가 난다).
- 단위 테스트용으로 `formatClock`을 export했다.

## 4) 집계 쿼리 무효화

### 티켓과 실제 코드가 다른 점 (중요)

티켓은 "주간 총 집중시간을 보여주는 `useWeeklyFocus.ts`"라고 적혀 있는데,
**`useWeeklyFocus`는 현재 어느 컴포넌트에서도 쓰이지 않는다** (`grep` 결과 정의 파일 외
참조 0건). 화면에 실제로 보이는 "총 집중 시간" 카드는 `MissionBoard`의 `StatCell`이고,
그 값은 `useDailyStats`(`["checkins", "today"]` → `/api/checkins`)에서 온다.
그리고 `/api/checkins`는 오늘 범위 `focus_sessions.duration_min`을 합산해 내려준다.

즉 티켓이 적은 `weeklyFocusQueryKey`만 무효화하면 **사용자에게 보이는 카드는 여전히
갱신되지 않는다.** 티켓 글자 그대로만 하면 DoD의 의도("새로고침 없이 갱신됨")를 못 채운다.

### 한 일

scope 안 파일(`useStartFocusSession.ts`)에서 둘 다 무효화했다.

```ts
queryClient.invalidateQueries({ queryKey: missionsQueryKey });   // 기존
queryClient.invalidateQueries({ queryKey: dailyStatsQueryKey }); // 추가 (보이는 카드)
queryClient.invalidateQueries({ queryKey: weeklyFocusQueryKey }); // 추가 (티켓 명시)
```

- `dailyStatsQueryKey` 추가는 티켓 문구를 넘어서는 판단이라 여기 남긴다.
  파일은 scope 안이고, 같은 원인(`duration_min` 확정)에서 나오는 같은 종류의 버그다.
- `weeklyFocusQueryKey`는 소비처가 없어 지금은 아무 네트워크 요청도 유발하지 않는다
  (TanStack Query는 관찰자가 없는 쿼리를 refetch하지 않음). 나중에 주간 카드를 붙이면
  그때부터 동작한다.
- 쿼리키 접두사 충돌 확인: `weeklyFocusQueryKey`는 `["focus-sessions","weekly"]`라
  `["focus-sessions","active"]`나 `["focus-sessions","paused-marker"]`를 건드리지 않는다
  (`["focus-sessions"]`로 뭉뚱그려 무효화하면 바로 위에서 `setQueryData`로 넣은 값을
  다시 날리게 되므로 일부러 피했다).
- FSD import 방향: features → entities라 위반 아님 (`useToggleMission`도 같은 패턴).

## 5) 모바일 — 재현하지 못함 (사람 확인 필요)

### 재현 시도와 실패 이유

**실기기/모바일 뷰포트에서 재현하지 못했다.** 이 세션에는 브라우저를 띄우고 조작할 수 있는
도구가 없고, `AUTH_GUARD_ENABLED = true`라 대시보드가 로그인 없이는 `/login`으로
리다이렉트된다. 로그인은 카카오/구글 OAuth뿐이라 헤드리스로 세션을 만들 수 없다.
그래서 "증상 → 원인" 확인 대신 **코드에서 모바일에만 불리하게 작용하는 지점을 찾아
고치는** 방식으로 접근했다.

### 가장 유력한 원인: 2번과 같은 뿌리

모바일 브라우저(특히 iOS 사파리)는 앱을 전환하거나 화면을 잠그면 백그라운드 탭의 JS를
**쓰로틀링이 아니라 아예 정지**시킨다. 기존의 "틱마다 +1" 방식에서는 이게
"타이머가 멈춰서 안 돌아간다"로 그대로 보인다 — 데스크톱에서는 "느리게 간다"로 보이던
증상이 모바일에서는 "작동 안 함"으로 보이는 것. 2번 수정(실제 시계 재계산 +
`visibilitychange`/`pageshow`/`focus` 복귀 처리)이 이 경우를 그대로 덮는다.
`pageshow`를 넣은 것도 모바일 사파리 bfcache 복귀 때문이다.

### 추가로 고친 것: 터치 타깃

타이머 컨트롤은 `Button size="sm"`(`py-1.75` + 12px 텍스트)이라 높이가 약 31px다.
iOS HIG 최소 권장(44px)과 WCAG 2.5.8에 모두 못 미쳐서, 실기기에서 탭이 자주 빗나간다.
"눌러도 아무 일도 안 일어난다"로 체감되기 쉬운 지점이다.

```tsx
const controlClassName = "min-h-11 flex-1 touch-manipulation sm:min-h-0";
```

- `min-h-11`(44px)은 모바일에서만 적용하고 `sm:` 이상은 기존 높이를 유지했다.
  데스크톱 패널까지 44px로 키우면 디자인이 바뀌므로.
- `touch-manipulation`은 더블탭 확대 대기(≈300ms)를 없애 첫 탭이 바로 먹히게 한다.
- `Button.tsx`는 scope 밖이라 건드리지 않고 호출부 `className`으로만 처리했다.
  (`cn()`이 단순 join이고 `Button` 기본 클래스에 `min-h`가 없어 충돌 없음)

### 확인하지 못해 남는 가능성

아래는 코드만 봐서는 배제하지 못했다. 실기기 확인 시 이것부터 보면 된다.

- 모바일 전용 레이아웃 간섭: 대시보드 하단의 `MobileTabBar`가 `fixed … z-40`이고 페이지에
  `pb-16`이 걸려 있다. 계산상 타이머 패널은 가려지지 않지만(패널 아래 `StreakBar`가 더 있음),
  기기별 safe-area에서는 다를 수 있다. 다만 이건 scope 밖 파일(`page.tsx`, `MobileTabBar.tsx`)이다.
- 네트워크/인증 문제(모바일에서만 세션 쿠키가 안 붙는 등)라면 타이머가 아니라 `/api/focus-sessions`
  호출 자체가 실패하고 스켈레톤에서 멈춘다. 이 경우 증상은 "타이머 작동 안 함"으로 같지만
  원인이 완전히 달라서 이 티켓 범위에서 고칠 수 없다. **실기기에서 개발자 도구로
  `/api/focus-sessions` 응답부터 확인해 주시기 바란다.**
