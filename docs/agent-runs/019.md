## 1. 측정 방법 (어떻게 쟀는가)

### 1-1. 측정 환경의 제약과 선택

| 고려한 방법 | 장점 | 문제점 | 채택 여부 |
| --- | --- | --- | --- |
| (a) 라우트 코드에 `console.time` 등 임시 로그를 직접 넣고 `npm run dev`로 브라우저에서 측정 | 티켓 문구 그대로 | `AUTH_GUARD_ENABLED = true`라 로그인 세션이 있어야 하고, 세션 없이 호출하면 proxy가 401을 반환해 라우트 본문까지 가지 않음. dev 모드는 첫 요청마다 컴파일 시간이 섞여 수치가 오염됨. 측정 후 로그를 다시 지워야 함 | ✗ |
| (b) 로컬 Supabase(`supabase start`)에 테스트 유저를 만들어 인증된 상태로 전체 흐름 측정 | AGENTS.md 권장 로컬 환경, 쓰기 경로까지 실측 가능 | **Docker 데몬이 꺼져 있어 사용 불가** (`failed to connect to the docker API`). 또한 로컬은 RTT가 ~1ms라 네트워크 왕복 비용이 드러나지 않음 | ✗ (불가) |
| (c) 공유 원격 dev 프로젝트에 테스트 유저를 생성해 실측 | 가장 실제에 가까움 | 여러 워크트리가 공유하는 원격 프로젝트에 데이터(auth 유저/세션 행)를 쓰는 행위라 부작용 위험. 사람 승인 없이 하지 않기로 함 | ✗ |
| **(d) 원격 실측(읽기 전용) + 왕복 지연 주입 하네스 조합** | 원격 프로젝트에 쓰기 없이 실제 RTT를 얻고, 쓰기 경로는 **실제 라우트 코드**를 그대로 돌리면서 직렬 왕복 수를 정확히 셈 | 쓰기 경로의 절대값은 "실측 RTT × 직렬 단계 수" 기반의 시뮬레이션 값 | **✓ 채택** |

(d)를 택한 이유: 이 티켓의 핵심 질문은 "어느 구간이 몇 번, 순차로 기다리느냐"이고, 개별 쿼리 실행 시간은
원격 실측에서 서버측 처리(`x-envoy-upstream-service-time=2ms`)가 거의 0이고 대부분이 네트워크 왕복임이
확인됐다. 따라서 "실측 RTT × 직렬 왕복 수"로 응답 시간이 거의 결정되며, 이 구조는 실제 라우트 코드를
그대로 실행해야 정확히 셀 수 있다. 라우트 코드를 건드리지 않고 **전역 `fetch`를 감싸서** 모든 Supabase
요청의 시작/종료 시각을 기록했기 때문에, 측정 후 지울 임시 로그도 남지 않는다(작업 내용 ⑥ 충족).

### 1-2. 측정 도구 (스크래치패드에만 두고 저장소에는 커밋 대상으로 넣지 않음)

1. **원격 프로브** (`probe.mjs`): 원격 Supabase에 anon(publishable) 키로 읽기 요청만 10회씩 보내 RTT 측정,
   JWKS 엔드포인트로 JWT 서명 방식 확인.
2. **원격 실측 하네스** (`remote.bench.test.ts`): 실제 라우트 핸들러(`GET()`/`POST()`)를 import해서
   실제 원격 Supabase에 대고 12회씩 실행(첫 회는 콜드로 따로 기록). `next/headers`의 `cookies()`만 빈
   쿠키 스텁으로 바꿔서 **세션 없는 anon 상태** → RLS 때문에 0행이 돌아오지만 쿼리 자체는 실제로 실행됨.
   쓰기가 일어나지 않는 경로만 실행(POST focus-sessions는 `stop` + 열린 세션 없음 → select 2회만 발생).
3. **왕복 지연 주입 하네스** (`sim.bench.test.ts`): 실제 라우트 코드 + 목 Supabase 클라이언트.
   쿼리/인증 호출 1건마다 RTT만큼 지연시키고 각 호출의 시작 시각을 기록해 "직렬 단계 수"를 계산.
   RTT는 ① 실측값 25ms(한국 ↔ 원격 Supabase), ② 리전 불일치 가정 190ms(서울 ↔ 미국 동부 일반적 RTT, **추정치**) 두 가지.
4. **getClaims 비용 측정** (`claims.bench.test.ts`): ES256 키쌍을 직접 생성해 서명한 JWT로
   `auth-js`의 `getClaims()`를 200회 호출, 네트워크 호출 횟수를 셈(fetch를 실패하도록 막아둠).

## 3. 원인 분석 결론

1. **(확인됨, 코드로 개선) missions POST의 불필요한 `getUser()`** — `console.log("SERVER SEES USER:", user, userError)`

   개인정보)를 서버 로그에 출력**하고 있었음.

   새 세션 insert → 오늘 세션 재조회. 이 중 update와 insert는 서로 결과에 의존하지 않음.
3. **(원인 아님) 인증 검증 비용** — ES256 로컬 검증 0.42ms, 네트워크 0회.

## 4. 변경 내용 — 고려한 방법과 선택 이유

### 4-1. `src/app/api/missions/route.ts` — POST의 `getUser()` + 개인정보 로그 제거

**문제**: 결과를 쓰지 않는 `supabase.auth.getUser()`가 insert 전에 순차로 await됨 → Auth 서버 왕복 1회 낭비 +
유저 정보 전체를 `console.log`로 출력.

| 고려한 방법 | 판단 |
| --- | --- |
| (a) `getUser()`를 `getClaims()`로 교체 | 로컬 검증이라 빠르지만, 결과를 여전히 쓰지 않음. proxy가 이미 같은 요청에서 검증했으므로 "중복 검증"을 싸게 바꾼 것일 뿐 의미 없음 |
| (b) `getUser()` 결과를 메모이즈 (React `cache` 등) | Route Handler에서는 React `cache`의 요청 단위 메모이즈가 적용되지 않고, 애초에 같은 요청에서 한 번만 호출되므로 메모이즈할 대상이 아님 |
| (c) `getUser()`와 insert를 `Promise.all`로 병렬화 | 왕복 시간은 줄지만 쓰지 않는 네트워크 호출과 개인정보 로그가 그대로 남음 |
| **(d) 호출과 로그를 제거** | **채택** |

**채택 이유 / 세션 검증을 생략한 게 아닌 근거**:
- 인증 검증은 여전히 2중으로 일어난다: ① `src/proxy.ts`가 모든 `/api` 요청에서 `getClaims()`로 JWT를 검증하고
  실패 시 401을 반환 ② PostgREST가 요청에 실린 JWT를 다시 검증하고 RLS(`auth.uid() = user_id`)를 적용.
- `user_id`는 마이그레이션 `20260915062237_default_user_id_to_auth_uid.sql`로 DB 기본값 `auth.uid()`가 채우므로
  라우트가 user를 알 필요가 없다.
- 즉 제거한 것은 "같은 요청 내 결과를 쓰지 않는 중복 검증"뿐이며, 티켓 작업 내용 ④("같은 요청 내 중복 호출만
  메모이즈, 세션 검증 자체는 생략하지 않음")의 취지에 맞는다. 메모이즈보다 제거가 맞는 이유는 (b) 참고.

### 4-2. `src/app/api/focus-sessions/route.ts` — start/resume의 update ∥ insert 병렬화

**문제**: `closeOpenSession`(select → update) → insert → `fetchTodaySession` 4단계 순차.

의존 관계 분석:
- select(열린 세션) → update: update에 열린 세션의 `id`와 `started_at`(duration 계산)이 필요 → **의존**
- update → insert: insert는 update 결과를 쓰지 않음. 닫을 행은 이미 `id`로 특정됨 → **독립**
  (DB에 "열린 세션은 1개" 같은 유니크 제약이 없음을 마이그레이션에서 확인 — 병렬 insert가 제약 위반을 낼 일 없음)
- 쓰기 → fetchTodaySession: 쓰기 결과가 반영된 최종 상태를 읽어야 함 → **의존**

| 고려한 방법 | 왕복 단계 | 판단 |
| --- | --- | --- |
| (a) 현행 유지 | 4 | — |
| **(b) update ∥ insert (`Promise.all`) + 부분 실패 시 보상 삭제** | **3** | **채택** |
| (c) (b) + 처음 select를 "열린 세션 OR 오늘 세션" 하나로 합치고, 최종 상태는 DB 재조회 없이 메모리에서 조립 | 2 | `toFocusSession`의 누적 시간 계산을 라우트가 직접 흉내내야 해서 DB 상태와 어긋날 위험이 큼. 코드 복잡도 대비 이득(1단계)이 작음 |
| (d) Postgres RPC 함수 하나로 close+insert+조회를 원자적으로 처리 | 1 | 가장 빠르고 원자적이지만 `supabase/migrations/` 추가가 필요 → **scope 밖**. 후속 티켓 제안으로만 남김 |
| (e) select와 fetchTodaySession을 처음부터 병렬로 | — | fetchTodaySession은 쓰기 이후 상태를 읽어야 하므로 불가 |

**(b)의 위험과 대응**: 순차일 때는 "마감(update) 실패 → insert 안 함 → 500"이었는데, 병렬로 보내면 update가
실패해도 insert는 이미 성공했을 수 있다. 그대로 두면 열린 세션이 2개가 되어 `toFocusSession`이 누적 시간을
계속 늘리고, 다음 `closeOpenSession`은 최신 1개만 닫아 고아 세션이 남는다. 그래서:
- insert를 `.select("id").single()`로 바꿔 새 행의 id를 돌려받고,
- update 실패 + insert 성공이면 그 id로 **보상 delete** 후 500 반환 → 순차 처리 때와 같은 최종 상태 유지.
- insert만 실패하면 기존처럼 500(기존 세션은 닫힌 상태 = 순차 때와 동일).
- 보상 delete는 실패 경로에서만 추가 왕복이 생기므로 정상 경로 성능에 영향 없음. RLS 정책
  `focus_sessions_own_rows`가 본인 행 삭제를 허용함을 확인.
- `stop`은 select → update → select가 전부 의존 관계라 병렬화 대상이 아니어서 구조만 정리(동작 동일).

**리팩터링**: `closeOpenSession(select+update)`를 `findOpenSession`(select)과 `closeSession`(update)으로
분리. 조회를 라우트 상단으로 올려야 update와 insert를 같은 `Promise.all`에 넣을 수 있기 때문.

### 4-3. `src/shared/lib/supabase/server.ts` — 변경 없음

측정 결과 `createClient()`는 쿠키를 읽어 클라이언트를 만들 뿐 네트워크 호출이 0건이었다. 같은 요청 내
`createClient()` 중복 호출도 각 라우트에서 1회뿐이라 메모이즈할 대상이 없다. 주석의 "전역 변수로 두지 말 것"
(Fluid compute 요청 간 세션 혼선 방지) 규칙도 유지해야 하므로 손대지 않았다.

## 6. 블로커 / 사람에게 넘길 사항

### 블로커 1 — 서버 함수(Vercel) ↔ Supabase 리전 확인 필요 (인프라, 코드로 해결 불가)

- 근거: 원격 Supabase는 한국에서 warm RTT 18~36ms, `cf-ray ...-ICN` → 서울(또는 인근) 리전으로 추정.
  반면 저장소에 `vercel.json`/리전 설정이 없어 Vercel 함수는 기본 리전(일반적으로 미국 동부 `iad1`)일 가능성이 높음.
- 영향(추정): 왕복 1회가 ~25ms → ~190ms. 수정 후에도 focus-sessions start는 590ms, 미션 추가는 196ms,
  거기에 브라우저 ↔ Vercel 왕복과 아래 6-3의 "변경 후 재조회" 요청이 더해져 체감 지연이 커짐.
- 에이전트가 확인하지 못한 것: Vercel 프로젝트의 실제 Function Region, Supabase 프로젝트의 실제 리전
  (Supabase MCP 서버가 인증되지 않아 조회 불가 — `/mcp`에서 supabase 인증 필요).
- 권장 조치(사람이 직접): Vercel 대시보드 → Settings → Functions → Function Region을 Supabase와 같은 리전
  (서울이면 `icn1`)으로 맞추거나 `vercel.json`에 `"regions": ["icn1"]` 추가. 인프라 설정이라 에이전트는 변경하지 않음.

### 전달 사항 — nag 라우트 (017 작업자 / 사람에게, 수정하지 않음)

`src/app/api/nag/route.ts`를 **읽기만** 했다. 구조상 GET/POST 모두
`collectNagAggregate`(4쿼리 `Promise.all`, 1단계) → `fetchLatestNagLog`(1단계) → 필요 시 OpenAI 생성
(`callOpenAI.ts` 타임아웃 8초) → `saveNagLog`(1단계)가 순차다.
- `collectNagAggregate`와 `fetchLatestNagLog`는 서로 독립으로 보여 `Promise.all`로 묶으면 왕복 1단계를 줄일 수 있음.
- 체감상 가장 큰 비용은 OpenAI 호출(초 단위)이며, 아래 6-3처럼 미션 토글/삭제마다 nag 쿼리가 무효화되어
  재생성 경로를 탈 수 있음. 017에서 함께 검토 권장.

### 참고 — scope 밖에서 발견한 체감 지연 요인 (후속 티켓 후보, 수정하지 않음)

1. **낙관적 업데이트 부재** (`src/features/*/model/use*.ts`): 토글/추가/삭제가 "PATCH/POST 응답 → `invalidateQueries`
   → GET 재조회 완료" 후에야 화면이 바뀜. 즉 한 동작에 HTTP 요청 2번이 순차로 걸림. `onMutate` 낙관적 업데이트를
   쓰면 클릭 즉시 반영 가능.
2. **토글/삭제 시 4개 쿼리 동시 무효화** (missions, dailyStats, streak, nag) — 특히 nag는 OpenAI까지 갈 수 있음.
3. **`src/proxy.ts`의 `console.log("PROXY RUNNING: ", pathname)`** — 모든 요청(정적 제외)마다 로그. 성능 영향은
   미미하지만 운영 로그 노이즈. proxy.ts는 scope 밖이라 그대로 둠.
4. **콜드스타트 571~740ms** — 서버리스 인스턴스가 새로 뜰 때 Supabase와 TLS 연결을 새로 맺는 비용. 리전 정렬 시 함께 줄어듦.
5. **개발 서버(`npm run dev`)에서 느낀 지연이라면** 라우트별 최초 컴파일 시간이 크게 섞이므로, 체감 측정은
   `npm run build && npm run start` 또는 배포 환경에서 하는 게 정확함.
6. **후속 개선안(DB)**: focus-sessions의 close+insert+조회를 Postgres RPC 하나로 묶으면 왕복 3→1단계 + 원자성 확보
   (마이그레이션 필요 → 별도 티켓).
