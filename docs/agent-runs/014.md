## 조사 결과 — 버그 2는 실제로는 "게이팅 버그"가 아니었음

`route.ts`를 다시 읽어봤는데, POST 핸들러는 처음부터 `latestLog.context.mode`를 비교하는
캐시 검사 없이 매번 `generateNagMessage`를 호출하고 있었음(즉 "mode 캐싱이 POST에도
적용된다"는 진단과 달리, 실제 코드에는 그 게이트가 없었음). 따라서 순수하게 "게이트를
없애는" 수정은 필요하지 않았음.

다만 아래 두 가지는 실제로 개선이 필요하다고 판단해서 반영함:

1. GET과 POST가 캐시 재사용 여부를 각각 인라인 조건문으로 따로 들고 있어서, "GET만 캐시
   재사용, POST는 항상 재생성"이라는 계약이 코드 구조상 명시적으로 드러나지 않았음. 나중에
   누군가 두 핸들러를 리팩터링하다가 실수로 POST에도 캐시 검사를 넣어버릴 위험이 있음.
2. 이 계약을 고정하는 회귀 테스트가 없었음 — 있었다면 애초에 이런 의심을 할 필요가 없었을
   것.

→ `resolveNagMessage(supabase, aggregate, latestLog, { forceRegenerate, requestedPersonaId })`
   라는 공용 함수로 캐시 재사용/강제 재생성 분기를 하나로 합치고, `forceRegenerate: false`는
   GET, `forceRegenerate: true`는 POST에서만 쓰도록 명시적으로 분리함. 동작 자체는 이전과
   동일(POST는 이미 항상 재생성하고 있었음)하지만, 계약이 코드로 드러나고 테스트로 고정됨.

참고: 실제 배포/로컬 환경에서 "거의 똑같은 문구"가 나오는 진짜 원인은 십중팔구
`OPENAI_API_KEY`가 `.env.local`에 없어서 매번 `pickFallbackMessage`(페르소나+mode당 고정
문구 4개 풀)로 폴백되고 있는 쪽일 가능성이 높음. 이건 `shared/lib/ai/**`, `.env` 관련
파일 영역이라 이번 스코프(`app/api/nag/**` 등) 밖이라 손대지 않음 — 사용자가 `.env.local`을
열어본 것도 이 가능성과 관련 있어 보임. `OPENAI_API_KEY`가 채워져 있는지 확인이 필요하면
별도로 알려달라고 요청할 것.

# generateNagMessage 중복 응답 필터링 로직 점검 (같은 티켓, 3차 요청)

## 받은 스펙 요약

- scope: `shared/lib/ai/**`
- 문제 진단: OpenAI 응답이 `history`(최근 문구 목록, 최대 5개)와 정확히 일치하면 폴백으로
  전환하는데, 폴백 문구도 같은 `history`에 기록되기 때문에, 한 번 폴백이 발생하면 이후
  정상적으로 생성된 새 OpenAI 응답까지 계속 "중복"으로 오판해 폴백으로 되돌리는 악순환이
  있을 수 있다는 의심.
- 요청: (1) `getRecentQuotes`가 몇 개/얼마나 기억하는지 확인 후 조정, (2) 완전 일치(===)
  비교를 느슨하게 바꾸거나 제거 검토, (3) 폴백 전환 빈도를 로그/테스트로 확인.
- DoD
  - [x] 재생성을 여러 번 눌러도 실제 OpenAI 응답이 대부분 그대로 사용됨
  - [x] 진짜 완전히 똑같은 문구가 나오는 극히 드문 경우에만 폴백 발동
  - (GET 캐시 유지는 이전 라운드에서 이미 처리된 별개 항목이라 이번엔 대상 아님)

## 원인 분석

의심이 정확했음. `callOpenAI.ts`의 `generateNagMessage`는:

1. `history = getRecentQuotes(mode, personaId)` — 인메모리(`globalThis`)에 최근 최대 5개
   문구를 보관(`nagHistory.ts`의 `HISTORY_LIMIT = 5`).
2. OpenAI 응답을 받으면 `history.includes(text)`로 **history 전체**와 완전 일치 여부를 검사.
   하나라도 겹치면 "중복"으로 보고 에러를 던져 폴백으로 전환.
3. 폴백으로 나간 문구도 `recordQuote(...)`로 **같은 history**에 기록됨.

문제는 폴백 문구 풀이 페르소나·mode당 딱 4개뿐이라는 점(`fallbackMessages.ts`). 이 4개는
"그 페르소나가 실제로 할 법한 전형적인 말투"를 그대로 문장으로 적어둔 것이라, OpenAI가
같은 페르소나·같은 맥락으로 여러 번 생성하다 보면 그 중 하나와 표현이 우연히 겹칠 가능성이
낮지 않음. 한 번이라도 (네트워크 오류·타임아웃 등 진짜 실패로) 폴백이 나가면:

- 그 폴백 문구가 history에 들어감
- 이후 OpenAI가 새로 생성한 정상 응답이 우연히 그 문구와 겹치면 → 또 "중복"으로 오판 →
  또 폴백 → 그 폴백도 history에 쌓임 → history가 점점 폴백 풀(4개)로 채워짐 → 이후
  응답들이 "중복"으로 걸릴 확률이 계속 올라가는 악순환.

## 적용한 수정

### 1) 완전 일치 비교 대상을 좁힘 (핵심 수정)

`src/shared/lib/ai/callOpenAI.ts` — OpenAI 응답의 "진짜 연속 중복" 여부를 **history 전체
(최대 5개, 폴백 문구 포함 가능)가 아니라, 실제로 가장 최근에 나간 문구 딱 1개**와만
비교하도록 바꿈(`getRecentQuotes(...)[0]`). "반복 금지" prompt 힌트(`buildNagPrompt`에
넘기는 `recentQuotes`)는 여전히 history 전체(최대 5개)를 그대로 씀 — 이건 LLM에게 "이런
표현은 피해줘"라고 부드럽게 유도하는 용도라 넓게 잡아도 부작용이 없음. 하드 리젝션(에러를
던져 폴백으로 강제 전환)만 "직전 문구와 완전히 같은가"로 좁힌 것.

이 변경으로:
- 폴백 문구 하나가 history에 들어가 있어도, 그 다음 정상 OpenAI 응답이 "직전 문구"가 아닌
  이상(즉 그 폴백 문구가 바로 방금 나간 게 아닌 이상) 절대 그걸로 인해 거부되지 않음 →
  악순환 차단.
- "진짜로 같은 문구가 연속으로 나온" 극히 드문 경우(모델이 우연히 바로 직전과 완전히 같은
  문장을 다시 낸 경우)는 여전히 잡아서 폴백으로 돌림 → DoD의 "극히 드문 경우에만 폴백" 요건
  유지.

### 2) HISTORY_LIMIT(5)은 그대로 둠, 용도 주석으로 명시

`nagHistory.ts`의 `HISTORY_LIMIT = 5`는 낮추지 않음. 하드 리젝션에는 더 이상 안 쓰이고
(위 수정으로 1개만 비교), 이제 남은 용도는 (a) prompt "반복 금지" 힌트, (b) 폴백을 다시
고를 때 최근 문구 제외(`pickFallbackMessage`의 `excludeQuotes`) 두 가지뿐인데, 둘 다
"완화된" 용도라 5는 적절한 크기라고 판단함(폴백 풀이 4개뿐이라 굳이 5보다 더 키울 이유도
없음). 대신 이 히스토리를 더 이상 하드 리젝션에 쓰면 안 된다는 걸 코드 주석으로 못박음
(다음에 누가 실수로 다시 `history.includes(text)`로 되돌리는 걸 방지).

### 3) 폴백 전환 시 로그 추가 + 테스트로 빈도/정확성 확인

- `catch` 블록에서 `console.warn`으로 "OpenAI 응답을 사용하지 못해 폴백으로 대체함" +
  실패 원인(에러 메시지)을 남김 — 운영 중 폴백이 얼마나/왜 발생하는지 나중에 로그로
  확인할 수 있게 함.
- `callOpenAI.test.ts`에 테스트 3개 추가:
  1. "서로 다른 OpenAI 응답을 5번 연속으로 받으면 매번 그대로 사용한다" — 수정 전 코드였다면
     history가 5개 찰 무렵부터 오탐 가능성이 생기는 시나리오인데, 수정 후엔 5번 다 그대로
     통과하는지 확인.
  2. "과거에 폴백 문구가 히스토리에 섞여 있어도, 다음 정상 OpenAI 응답을 폴백으로 되돌리지
     않는다" — 악순환 재현 테스트. history에 "더 예전 폴백 문구"와 "그 다음의 직전 문구"를
     순서대로 심어두고, OpenAI가 (직전 문구가 아니라) 그 "더 예전 폴백 문구"와 우연히 같은
     내용을 반환하는 상황을 모킹 → 그대로 받아들여지는지 확인. 수정 전 비교 로직
     (`history.includes(text)`)으로 실제로 되돌려서 이 테스트가 실패하는 것까지 직접
     확인한 뒤 다시 수정된 코드로 복원함(단순 추측이 아니라 실제 반증 테스트로 검증).
  3. "진짜 완전히 똑같은 문구가 연속으로 나오는 경우에만 폴백으로 전환한다" — 매 호출마다
     동일한 문구를 반환하도록 모킹 → 첫 호출은 그대로 통과, 두 번째 호출(직전과 완전 동일)만
     폴백으로 전환되는지 확인.
- 위 새 테스트들과 기존 테스트가 `globalThis.__nagQuoteHistory`(모듈 전역 상태)를 파일 내에서
  공유해 서로 오염시킬 수 있어서(기존 테스트 스위트도 사실 이 문제에 알게 모르게 노출돼
  있었음), `beforeEach`로 매 테스트마다 히스토리를 초기화하도록 추가함 — 이번 버그와 같은
  종류의 문제(과거 상태가 다음 케이스를 오염시킴)를 테스트에서도 막기 위한 조치.
