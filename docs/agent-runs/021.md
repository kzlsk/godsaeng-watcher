## 1. 받은 티켓 스펙 요약

  3. 두 기기(또는 두 창)로 동시 테스트해 반영 지연 시간을 이 로그에 남긴다.
- scope: `src/app/providers.tsx`, (필요시) 각 엔티티 쿼리 훅의 `refetchInterval`/`staleTime`
  설정 (`useMissions.ts`, `useFocusSession.ts`, `useWeeklyFocus.ts`, streak 관련 훅).
  **단 `useStartFocusSession.ts`는 018이 건드리므로 수정 금지.**

## 3. 설계 판단과 그 근거

### 3-1. `providers.tsx`에 전역 `refetchInterval`을 걸지 않은 이유 (가장 중요)

처음에는 `defaultOptions.queries.refetchInterval`에 한 줄 넣는 게 가장 간단해 보였다.
**그렇게 하면 018의 일시정지 기능이 조용히 깨진다.**

`src/entities/focus-session/model/pausedMarker.ts`의 `usePausedMarker`는 서버를 호출하지 않는
"가짜 쿼리"다. React Query 캐시를 전역 상태처럼 쓰려고 `queryFn: () => null`,
`staleTime: Infinity`로 선언돼 있다. 즉 이 쿼리가 다시 실행되면 **일시정지 마커가 null로 날아간다.**

그리고 `refetchInterval`은 `staleTime`을 전혀 보지 않는다. 설치된 query-core 5.102.8 소스를
직접 확인했다 (`node_modules/@tanstack/query-core/build/modern/queryObserver.js`):

```js
#updateRefetchInterval(nextInterval) {
  ...
  this.#refetchIntervalId = timeoutManager.setInterval(() => {
    if (this.options.refetchIntervalInBackground || focusManager.isFocused()) this.#executeFetch();
  }, this.#currentRefetchInterval);
}
```

`isStale` 검사 없이 `#executeFetch()`로 직행한다 → `staleTime: Infinity`로도 막히지 않는다.
전역 `refetchInterval`을 걸었다면 주기마다 `pausedMarker`의 `queryFn`이 돌면서
일시정지 중인 타이머가 저절로 다시 흐르기 시작했을 것이다.

**그래서 전역에는 포커스 동기화만 켜고, 폴링은 훅별로 명시했다.** 폴링을 받을 쿼리를
한 군데에서 선언하지 못하는 건 아쉽지만, 가짜 쿼리까지 싹 긁어가는 전역 설정보다 안전하다.

### 3-2. `refetchOnWindowFocus: true`는 왜 `pausedMarker`를 깨지 않는가

같은 걱정을 포커스 쪽에도 해봤는데, 이쪽은 안전하다. 같은 파일의 포커스 경로는
`refetchInterval`과 달리 `isStale`을 거친다.

```js
function shouldFetchOn(query, options, field) {
  if (... && resolveQueryValue(options.staleTime, query) !== "static") {
    const value = typeof field === "function" ? field(query) : field;
    return value === "always" || value !== false && isStale(query, options);
  }
  return false;
}
```

`refetchOnWindowFocus: true`는 "**stale한 쿼리만**" 다시 받아온다는 뜻이다.
`pausedMarker`는 `staleTime: Infinity`라 영원히 stale이 되지 않으므로 포커스 복귀로
`queryFn`이 재실행되지 않는다. 4-1의 하네스 Phase 4에서 실측으로도 확인했다
(포커스 blur/focus를 왕복시켜도 `queryFn` 재실행 0회, 마커 그대로 생존).

### 3-3. `staleTime`을 30초 → 10초로 낮춘 이유

3-2에서 본 대로 `refetchOnWindowFocus`는 stale한 쿼리만 갱신하므로, **`staleTime`이 사실상
포커스 동기화의 하한**이 된다. 30초로 두면 "폰에서 고치고 PC 창으로 돌아왔는데 30초가 안 지나서
아무 일도 일어나지 않는" 구간이 생긴다. 티켓이 요구한 폴링 주기(15~30초)보다 확실히 짧게
10초로 낮춰, 포커스 복귀가 거의 항상 실제 갱신으로 이어지게 했다.

`refetchInterval`은 `staleTime`과 무관하게 돌기 때문에(3-1) 이 변경이 폴링 주기를 흔들지는 않는다.

### 3-4. 스코프 판단: `useDailyStats.ts`를 포함시킨 이유

scope 목록에 이름이 명시된 건 `useMissions` / `useFocusSession` / `useWeeklyFocus` /
streak 훅이고, `useDailyStats.ts`는 없다. 그래도 포함했다. 근거는 세 가지다.

1. scope 문구가 "(필요시) **각 엔티티 쿼리 훅의** refetchInterval/staleTime 설정"으로
   열려 있고, `useDailyStats`는 그 범주의 엔티티 쿼리 훅이다.
2. `MissionBoard.tsx`의 통계 패널은 **같은 줄에** `useMissions`(완료율)와
   `useDailyStats`(총 집중 시간)를 나란히 그린다. 미션만 폴링하면 완료율은 갱신되는데
   그 옆 총 집중 시간은 멈춰 있어, 한 패널 안에서 숫자가 서로 어긋나 보인다.
3. 이미 코드베이스가 이 둘을 한 묶음으로 취급한다. `useToggleMission`의 `onSuccess`는
   `missions` / `dailyStats` / `streak` / `nag` **네 개를 같이 무효화**한다. 즉 티켓이 말한
   "대시보드 핵심 쿼리"의 실제 구성은 이 네 개이고, `dailyStats`가 그중 하나다.

되돌리는 비용은 한 줄 삭제다. 과한 확장이라고 보시면 그 줄만 지우면 된다.

### 3-5. `useWeeklyFocus`는 scope에 명시돼 있어 넣었지만, 현재 사용처가 없다

`grep -rn "useWeeklyFocus" src`로 확인한 결과 **이 훅을 쓰는 컴포넌트가 하나도 없다**
(`/api/focus-sessions/weekly` 라우트와 훅 파일만 존재). 마운트되지 않으므로 추가한
`refetchInterval: 30_000`은 현재 아무 요청도 만들지 않는다. scope에 이름이 적혀 있어서
설정은 넣어뒀고, 나중에 주간 집중 위젯이 붙으면 그때부터 동작한다.
(= 4-2의 요청량 계산에는 포함하지 않았다.)

### 3-6. 주기를 20초 / 30초로 나눈 기준

| 쿼리 | 주기 | 이유 |
| --- | --- | --- |
| 미션 목록, 오늘 통계, 집중 세션 | 20초 | 사용자가 직접 토글/추가/삭제하는 값이라 체감 지연이 가장 중요 |
| 스트릭 | 30초 | 하루 단위로 바뀌는 값이라 초 단위 신선도가 의미 없음 |
| 쓴소리 | 30초 | 폴링 대상 중 가장 비싼 엔드포인트 (아래) |

`GET /api/nag`은 한 번 호출될 때마다 `missions` + `focus_sessions`(오늘) +
`focus_sessions`(주간) + `checkins`(최대 400행) + `nag_logs`를 집계한다. 그래서 허용 범위
(15~30초)의 **가장 느린 쪽**을 골랐다.

**OpenAI 비용은 폴링 주기만큼 늘지 않는다**는 걸 라우트를 읽고 확인했다.
`resolveNagMessage`는 `(mode, personaId, date)`가 같으면 `nag_logs`의 최신 문구를 그대로
재사용하고, OpenAI는 `mode`가 바뀐 순간(= 미션을 전부 끝내 fail↔success가 뒤집힐 때)에만
호출된다. 즉 AI 호출 횟수는 하루 몇 번의 mode 전환에 묶여 있고, 폴링이 늘리는 건 DB 집계
비용뿐이다. (다만 레이스 하나를 발견했다 — 5-2 참고.)

### 3-7. 018(집중 타이머) 충돌 분석 — DoD 3번

`FocusTimerPanel.tsx`의 재동기화는 **참조 비교**로 걸려 있다.

```js
const isPendingLocalPause = status === "paused" && pausedMarker !== null;
if (session && session !== syncedSession && !isPendingLocalPause) {
  setSyncedSession(session);
  setStatus(session.status === "running" ? "running" : "idle");
  setElapsedSeconds(session.elapsedSeconds);   // ← 로컬 1초 카운터를 덮어쓴다
}
```

여기에 폴링을 걸면 매 주기마다 이 줄이 돌아 1초 카운터를 덮어쓰는 게 아닌지 확인했다.
결론은 "값이 실제로 바뀔 때만 돈다"이고, 세 경우로 갈린다.

1. **응답이 이전과 완전히 같을 때 → 아무 일도 안 일어난다.**
   TanStack의 structural sharing이 기본으로 켜져 있어(`utils.js`의
   `options.structuralSharing !== false` → `replaceEqualDeep`), 깊은 값이 같으면 **이전 객체
   참조를 그대로 유지**한다. 그래서 `session !== syncedSession`이 아예 성립하지 않는다.
   idle 상태에서 폴링이 돌아도 화면은 건드려지지 않는다.
2. **running 중일 때 → 재동기화되지만, 그게 오히려 교정이다.**
   서버의 `elapsedSeconds`는 `started_at` 기준으로 계산되므로 주기마다 값이 달라지고
   재동기화가 일어난다. 다만 이건 로컬 카운터를 **서버 기준으로 되맞추는** 동작이다.
   `setInterval` 자체 드리프트와 브라우저의 백그라운드 탭 스로틀링 때문에 로컬 카운터는
   시간이 갈수록 실제보다 뒤처지는데, 폴링이 그걸 20초마다 잡아준다.
   **1초 카운트 로직 자체(`useEffect` + `setInterval(…, 1000)`)는 한 줄도 건드리지 않았다.**
3. **로컬 일시정지 중일 때 → 재동기화를 건너뛴다.**
   일시정지는 DB에 없는 프론트 전용 상태라 서버는 계속 `running`으로 보고하는데,
   `isPendingLocalPause` 가드가 이미 그 경우를 막아두고 있다. 폴링이 이 가드를 우회하지 않는다.
   (3-1에서 전역 `refetchInterval`을 포기한 게 바로 이 가드의 전제인 `pausedMarker`를
   지키기 위한 것이다.)

부수적으로 확인한 것: `deadlineLabel`이 `now` 기준 문자열("3h 12m")이라 idle 상태에서도
1분에 한 번쯤 참조가 바뀐다. 이때 일어나는 재동기화는 표시값을 DB 누적값으로 되돌리는 것뿐이라
무해하다.

## 4. 검증 결과

### 4-1. 클라이언트 폴링 메커니즘 실측 (하네스)

`providers.tsx`의 기본값과 훅의 `refetchInterval`을 그대로 재현한 하네스를 **실제 타이머로**
돌려서, 설정이 의도대로 동작하는지 측정했다. (스크래치패드에서 실행 — 저장소에는 파일을
추가하지 않았다. 이유는 5-5 참고.)

```
  0.0s isServer=false (false여야 refetchInterval 타이머가 스케줄된다)
  0.0s   -> /api/missions fetch #1
  1.0s 일시정지 마커 설정됨 (018의 pause 상태 재현)
  1.0s === Phase 1: 포커스 상태로 45초 대기 (20초 폴링이 2회 돌아야 함) ===
 20.0s   -> /api/missions fetch #2
 40.0s   -> /api/missions fetch #3
 45.0s PASS 45초 동안 20초 폴링이 2회 발사 (실측 2회)
 45.0s PASS 폴링 간격 20초±1.5초 (실측 20.01s, 20.00s)
 45.0s === Phase 2: 백그라운드(blur) 25초 — 폴링이 멈춰야 함 ===
 70.0s PASS blur 중 요청 0건 (실측 0건) — refetchIntervalInBackground 기본 false
 70.0s === Phase 3: 포커스 복귀 — stale한 쿼리는 즉시 재요청 ===
 70.0s   -> /api/missions fetch #4
 71.5s PASS 포커스 복귀 직후 /api/missions 1회 재요청 (실측 1건)
 71.5s === Phase 4: pausedMarker가 포커스 복귀로 초기화되지 않았는지 ===
 73.4s PASS pausedMarker queryFn 재실행 0회 (실측 0회)
 73.4s PASS 일시정지 마커 생존 ({"missionId":"m1","pausedAt":"..."})
 73.4s === 전체 통과 ===
```

읽는 법:

- **Phase 1**: 20초 주기가 실제로 20.01s / 20.00s 간격으로 발사된다.
- **Phase 2**: 창이 가려진 동안 **요청이 0건**이다. `refetchIntervalInBackground` 기본값이
  `false`라서 query-core가 타이머를 돌리되 `focusManager.isFocused()`가 false면 실행을
  건너뛴다 (3-1의 코드 인용 참고). 과도한 폴링 방어가 라이브러리 차원에서 보장된다는 뜻이다.
- **Phase 3**: 포커스가 돌아오자마자(같은 틱, 로그상 70.0s) 재요청이 나간다 → "다른 창 보다가
  돌아오면 바로 최신"이 동작한다.
- **Phase 4**: 3-2의 분석을 실측으로 확인. 018의 일시정지 마커가 살아남는다.

하네스를 짜면서 내 실수 두 개를 먼저 잡았는데, 둘 다 기록해 둘 가치가 있다.

1. 첫 실행에서 폴링이 **0회**였다. 원인은 `#shouldScheduleTimer`가
   `!isServer() && …`를 요구하고, `isServer`는 모듈 로드 시점에
   `typeof window === "undefined"`로 한 번 계산되는 **상수**라는 점이다. Node에서는 항상
   `isServer=true`가 되어 타이머가 아예 스케줄되지 않는다. import보다 먼저 `window`/`document`를
   심어야 한다. → **부수 수확: `refetchInterval`은 브라우저에서만 도는 설정이라 SSR 쪽에
   영향이 없다.**
2. 포커스 복귀 재요청도 0회였다. `focusManager` 구독은 `QueryClient.mount()`에서 일어나고
   (React에서는 `QueryClientProvider`가 호출해 준다), 하네스에서는 직접 불러줘야 했다.

### 4-2. 요청량 — "과도한 폴링" DoD 점검

현재 대시보드에 실제로 마운트되는 쿼리만 센다. `useStreak`은 3개 컴포넌트에서 쓰이지만
`queryKey`가 같아 하나의 쿼리로 합쳐진다. `useWeeklyFocus`는 사용처가 없어 0건(3-5).

| 엔드포인트 | 주기 | 분당 요청 |
| --- | --- | --- |
| `/api/missions` | 20초 | 3 |
| `/api/checkins` | 20초 | 3 |
| `/api/focus-sessions` | 20초 | 3 |
| `/api/streak` | 30초 | 2 |
| `/api/nag` | 30초 | 2 |
| **합계 (포커스된 대시보드 1개당)** | | **13회/분 ≒ 4.6초에 1건** |

- 창을 가리거나 모바일에서 화면을 끄면 **0회/분**으로 떨어진다 (4-1 Phase 2).
- `npm run build` 결과 API 라우트 7개가 전부 `ƒ (Dynamic)`이다. 즉 폴링 1건 = 실제 서버 실행 +
  Supabase 조회 1회이고, 중간 캐시 레이어가 없다. 019 티켓이 다룬 API 지연 수치를 그대로 더해야
  한다.
- 체감상 "탭 하나 열어두면 5초에 1건" 수준이라 성능 저하로 보일 양은 아니라고 판단했다.
  더 줄여야 하면 `/api/nag`을 60초로 빼는 게 가장 효과가 크다(가장 무거운 쿼리, 가장 느리게
  바뀌는 값).

### 4-3. 프로덕션 빌드

`npm run build` 통과 (Next.js 16.3.4 / Turbopack, 11.0s 컴파일). 라우트 목록상 `/`와 API 7개가
Dynamic, `/login`과 `/_not-found`가 Static으로 이전과 동일하다.

### 4-4. 참고한 Next.js 문서

AGENTS.md 지시대로 이 버전에 묶여 있는
`node_modules/next/dist/docs/01-app/02-guides/client-side-data-fetching/tanstack-query.md`를
읽었다. 이번 변경(클라이언트 컴포넌트 안의 QueryClient 기본값 조정)과 충돌하는 내용은 없었다.

문서는 프로바이더를 `useState` 대신 모듈 레벨 `browserQueryClient`로 들고 있으라고 권하는데,
현재 `providers.tsx`는 `useState(() => new QueryClient())` 패턴이다. 둘 다 "서버 렌더마다 새
클라이언트 / 브라우저에서는 재사용"을 만족하는 표준 패턴이고, 이건 이번 티켓 이전부터 있던
구조라 **건드리지 않았다** (스코프 밖이고 동기화와 무관).

## 5. 못 한 것 / 블로커 / 후속 제안

### 5-1. 블로커: 실제 두 기기 동시 로그인 테스트 (티켓 작업 내용 3번)

**실측 지연 시간을 실제 로그인 상태로 재보는 건 이 세션에서 못 했다.** 이유를 그대로 적는다.

- 로그인이 카카오/구글 OAuth다. 비대화형 세션에서 두 기기(두 창)로 동시 로그인하는 플로우를
  재현할 수 없다.
- 이 워크트리의 `.env.local`은 **원격 Supabase 프로젝트**를 가리킨다. AGENTS.md는 로컬 개발에
  `supabase start`를 쓰라고 했는데, 이 환경에는 Docker 데몬이 떠 있지 않고 supabase CLI도
  설치돼 있지 않아 로컬 인스턴스를 띄울 수 없었다. 원격 dev 데이터에 테스트 데이터를 쓰거나
  `/api/nag`을 반복 호출해 OpenAI 키를 소모하는 건 승인 없이 할 일이 아니라고 판단해
  하지 않았다.

그래서 4-1처럼 **내가 바꾼 부분(클라이언트 폴링 메커니즘)은 실측**하고, 서버 왕복이 끼는
구간은 아래 분석값 + 사람이 확인할 절차로 남긴다.

**예상 반영 지연 시간** (아래 값 + API 왕복 시간):

| 데이터 | 두 창을 나란히 띄워둔 채 방치 | 다른 창 보다가 돌아올 때 |
| --- | --- | --- |
| 미션 목록 / 오늘 통계 / 집중 세션 | 0~20초 (평균 ~10초) | 즉시 (<1초) |
| 스트릭 / 쓴소리 | 0~30초 (평균 ~15초) | 즉시 (<1초) |

→ 최악 30초 + 왕복. DoD의 "수십 초 이내면 1차 통과"를 만족하는 설계값이다.

**"두 창 나란히"가 왜 되는지** (헷갈리기 쉬운 부분): query-core의 `focusManager`는
`focus`/`blur`가 아니라 **`visibilitychange`만** 듣고,
`isFocused()`는 `document.visibilityState !== "hidden"`이다. 그래서 한 화면에 창 두 개를
나란히 띄우면 키보드 포커스가 없는 쪽도 `visible`이라 **양쪽 다 폴링한다.** 반대로 최소화하거나
다른 탭에 가려지면 `hidden`이 되어 멈춘다(= 모바일에서 화면 끄거나 앱 전환하면 멈춤 → 배터리·
데이터 보호).

**사람이 확인할 절차** (10분이면 됨):

1. `npm run dev` → 창 A와 창 B에 같은 계정으로 로그인하고, 두 창을 **겹치지 않게 나란히** 둔다
   (위로 겹치거나 최소화하면 가려진 쪽 폴링이 멈추므로 주의).
2. 창 A에서 미션을 하나 체크한다. 창 B의 완료율/미션 목록이 **20초 안에** 바뀌는지 본다.
3. 창 B에서 집중 시작 → 창 A의 타이머가 20초 안에 "진행 중"으로 바뀌는지 본다.
4. 창 B를 다른 앱으로 가린 뒤 창 A에서 미션을 바꾸고, 창 B를 다시 띄웠을 때 **1초 안에**
   반영되는지 본다 (포커스 동기화 경로).
5. DevTools Network에서 요청량이 4-2 표(13회/분)와 비슷한지 확인한다.
6. **018 회귀 확인**: 타이머를 running으로 두고 일시정지 → 다른 탭 갔다 돌아오기 → 20초 이상
   기다리기. 일시정지가 저절로 풀려 숫자가 다시 흐르면 안 된다 (4-1 Phase 4가 이걸 코드
   차원에서 보장하지만, 실제 화면으로도 한 번 봐주면 좋다).

### 5-2. 발견한 기존 레이스 — 폴링이 확률을 올린다 (수정 안 함, 스코프 밖)

`GET /api/nag`은 `mode`가 뒤집힌 순간에만 OpenAI를 호출하고 결과를 `nag_logs`에 insert한다.
이 구간에 락이 없어서, **두 기기가 거의 동시에 폴링하면 양쪽이 각각 OpenAI를 호출하고
`nag_logs`에 두 행이 쌓일 수 있다.** 원래도 수동 새로고침을 두 번 빠르게 하면 재현되는
레이스지만, 폴링을 켜면 발생 확률이 올라간다.

영향은 "하루에 몇 번 있는 mode 전환 시점에 AI 호출이 1회 더 나가고 로그가 한 줄 더 쌓임"
정도이고, 사용자 화면은 둘 중 최신 것으로 수렴한다. 고치려면 `app/api/nag/route.ts`를
건드려야 해서(스코프 밖) **손대지 않고 여기 기록만 남긴다.** 후속 티켓 후보.

### 5-3. 알려진 한계: 일시정지는 기기 간 동기화되지 않는다

`pausedMarker.ts` 주석에 적혀 있듯 "일시정지"는 DB에 없는 프론트 전용 상태다. 그래서
**기기 A에서 일시정지해도 서버는 계속 `running`으로 보고하고, 기기 B 화면에서는 타이머가
계속 흐르는 것으로 보인다.** 폴링이 만든 버그가 아니라 원래 있던 비대칭인데, 동기화를 켜면
더 눈에 띈다. 제대로 고치려면 일시정지를 DB 스키마에 반영해야 하고 이건 018/후속 티켓 영역이라
건드리지 않았다.

### 5-4. Supabase Realtime 검토 결과 → 후속 티켓 권고 (티켓 작업 내용 2번)

검토했고, **이번 티켓에서는 하지 않는 쪽**으로 판단했다. 티켓이 허용한 escape hatch
("난이도가 과하면 폴링으로 먼저 처리하고 후속 티켓으로 남긴다")를 쓴다.

제대로 붙이려면 최소 네 가지가 필요하다.

1. **마이그레이션 추가**: 현재 저장소에는 realtime publication 설정이 전혀 없다.
   `supabase/migrations/` 3개 파일에 realtime 언급이 없고, `supabase/config.toml`에
   `[realtime]` 섹션만 있다. `alter publication supabase_realtime add table …`를 넣는
   마이그레이션이 필요하다.
2. **구독 Provider 신규 파일**: 채널을 열고 `postgres_changes`를 받아
   `queryClient.invalidateQueries`로 연결하는 코드.
3. **RLS 보호 테이블 구독 처리**: 모든 테이블에 `auth.uid() = user_id` 정책이 걸려 있으므로
   private channel + `realtime.setAuth` 처리가 필요하다.
4. 폴링과의 역할 정리 (Realtime이 붙으면 `refetchInterval`은 백업 용도로 늘리는 게 맞다).

1번과 2번이 **스코프 밖**이고(마이그레이션 파일 / 신규 파일), 특히 1번은 AGENTS.md의
"여러 워크트리에서 동시에 원격 dev 프로젝트에 마이그레이션을 적용하지 않는다"에 정면으로
걸린다. 이 워크트리의 `.env.local`이 원격 프로젝트를 가리키는데 로컬 Supabase를 띄울 수도
없어서(5-1), 마이그레이션을 안전하게 검증할 방법도 없었다. 그래서 **직접 진행하지 않고
여기 기록만 남긴다.**

### 5-5. 단위 테스트를 추가하지 않은 이유

AGENTS.md의 "새 로직에는 단위 테스트를 추가한다"에 걸리는 항목이라 짚어둔다.
이번 변경은 새 로직이 아니라 **쿼리 옵션 값 변경**이고, 가장 테스트하고 싶었던 것
(3-2의 "포커스 복귀가 일시정지 마커를 깨지 않는다")은 React 훅을 렌더해야 확인할 수 있다.
그런데 이 저장소에는 `@testing-library/react`가 없고 `vitest.config.mts`의
`environment`가 `"node"`다. 훅을 렌더하지 못하니 테스트 안에서 옵션을 다시 손으로 적는
형태가 되는데, 그러면 실제 훅이 바뀌어도 통과하는 무의미한 테스트가 된다.

의존성 추가와 vitest 환경 변경은 명백히 스코프 밖이라 하지 않았다. 대신 같은 내용을
4-1의 하네스로 실측해 결과를 이 로그에 남겼다. 후속 제안: `@testing-library/react` +
`jsdom`을 도입하는 별도 티켓에서 이 성질(일시정지 마커 생존, 폴링 주기)을 회귀 테스트로
고정하는 게 좋다.
