## 설계 판단

### 1. "일시정지는 DB에 반영하지 않는다" 구현 방법

일시정지를 API 호출 없이 순수 프론트 상태로 처리하면, `running`에서 연 세그먼트(`started_at`만
있고 `ended_at`은 없음)가 일시정지 중에도 DB엔 계속 "열린 채"로 남는다. 이 상태에서 재개/중지를
누르면 서버는 그 세그먼트를 닫아야 하는데, 닫는 시점을 "지금"으로 하면 일시정지해 있던 시간까지
집중 시간으로 잘못 합산된다. 그래서:

- 클라이언트가 일시정지를 누른 **정확한 시점**(`pausedAt`)을 로컬 상태로만 기록해두고,
- 재개(`action: "resume"`) 또는 (일시정지 중) 중지(`action: "stop"`) 요청에 `endedAt`으로 그
  시점을 실어 보내서, 서버가 "지금"이 아니라 그 시점으로 기존 세그먼트를 닫도록 함.
- 일시정지를 거치지 않고 바로 중지하는 경우엔 `endedAt`을 보내지 않고 서버가 기본값(지금)을 씀.

이 방식대로 `app/api/focus-sessions/route.ts`의 `closeOpenSession`이 `endedAt: Date`를 인자로
받도록 바꾸고, POST 바디에 선택적 `endedAt` 필드를 추가함.

### 2. `features/start-focus-session/**`를 건드리지 않기 위한 선택

기존에 시작/일시정지/재개/중지를 모두 처리하던 훅(`src/features/start-focus-session/model/useStartFocusSession.ts`)은
`{missionId?, action}`만 받는 타입이라 위 `endedAt` 확장을 넣으려면 그 파일을 고쳐야 하는데,
`features/start-focus-session/**`는 이번 티켓 scope 밖임. 그 훅은 `MissionItem`(미션 목록의
"▶ 집중" 버튼, `action: "start"`만 보냄)이 여전히 그대로 쓰고 있어 손대지 않았고, 대신
`entities/focus-session/model/useUpdateFocusSession.ts`를 새로 만들어 `FocusTimerPanel` 자신의
시작/재개/중지 버튼이 이 새 훅(= `{missionId?, action: start|resume|stop, endedAt?}`)을 쓰도록
분리함. 두 훅이 거의 같은 모양이라 코드 중복이 생기지만(아래 블로커 참고), scope 경계를 지키는
쪽을 우선함. 둘 다 같은 쿼리 키(`focusSessionQueryKey`)에 `setQueryData`로 반영하므로, 미션
목록에서 시작한 세션도 `FocusTimerPanel`에 그대로 반영됨.

### 3. `toFocusSession`이 "중지 후"를 `idle`로 판정하도록 수정

일시정지가 더 이상 DB에 흔적을 남기지 않으므로, 서버 입장에서는 "열린 세그먼트가 있으면
running, 없으면 idle"만 판단할 수 있음(paused는 순수 프론트 상태). `mapFocusSessionRow.ts`의
`latest.ended_at ? "paused" : "running"`을 `latest.ended_at ? "idle" : "running"`으로 수정.

### 4. 미션 완료 체크 시 화면만 0으로

`useToggleMission`을 건드리는 대신(스코프 밖), `FocusTimerPanel`이 `useMissions()`로 미션
목록을 읽어 `session.missionId`와 일치하는 미션의 `isCompleted`를 확인하고, 완료 상태면 표시용
값(`displaySeconds`)만 0으로 덮어씀. 내부 `elapsedSeconds`/DB는 그대로 유지되어 "완료 체크
해제" 같은 조작을 해도 데이터 손실이 없음.

### 5. 렌더 중 상태 동기화 — 기존 코드와 동일한 패턴 유지

`useEffect` 안에서 `setState`로 서버 세션을 로컬 상태에 동기화하는 방식은 이 프로젝트의
`eslint-plugin-react-hooks`(React Compiler 계열 규칙, `react-hooks/set-state-in-effect`)에서
에러로 걸림. 기존 코드(수정 전 `FocusTimerPanel.tsx`)도 이미 "렌더 중 조건부 setState"
패턴(React 공식 문서의 "adjusting state when a prop changes")을 쓰고 있었어서 동일한 패턴을
그대로 확장함 — `session`이 바뀌었고 로컬이 `paused`가 아닐 때만 동기화.

   `useUpdateFocusSession.ts`로 통합하는 정리가 필요함.
2. **일시정지 중 페이지를 새로고침하면 화면 숫자가 튐**: 일시정지는 순수 프론트 상태라
   새로고침하면 사라짐 — 서버는 여전히 세그먼트가 "열려 있다"고 보고(`status: "running"`)
   하므로, 새로고침 직후엔 일시정지해 있던 시간까지 포함된 값으로 다시 표시됨. DB
   스키마에 "일시정지" 자체를 표현하는 컬럼이 없다는 010 티켓의 블로커 3과 같은 근본
   원인이고, 이번 DoD 항목(반복 시작/일시정지/재개/중지, actualFocusMinutes 정확성)엔
   새로고침 시나리오가 없어 이번 스코프에서 해결하지 않음. 필요하면 스키마 변경(예:
   `paused_at` 컬럼 추가)이 있는 별도 티켓에서 다뤄야 함.
3. **일시정지 중 다른 미션으로 전환하면 시간이 잘못 합산될 수 있음**: `MissionItem`의
   "▶ 집중" 버튼은 `endedAt` 없이 바로 `action: "start"`를 보내므로, A 미션을 일시정지한
   채로 B 미션의 "▶ 집중"을 누르면 서버가 A의 열린 세그먼트를 "지금"(일시정지 이후
   경과한 시간 포함)으로 닫아버림. `MissionItem`/`features/start-focus-session/**`가 scope
   밖이라 고치지 못했고, 블로커 1의 통합 작업과 함께 해결하는 게 자연스러움.
4. **브라우저 end-to-end 검증 미완료**: 위 "브라우저 검증 관련" 참고. 사람이 직접
   로그인해서 실제 클릭 흐름과 숫자 변화를 확인하거나, 로그인 세션을 제공해주면 이어서
   검증 가능함.

## 추가 변경 — 오늘 범위 복원 + 블로커 1/3 해결

같은 브랜치에서 이어진 후속 요청. scope: `widgets/FocusTimerPanel.tsx`,
`features/start-focus-session/**`, `entities/focus-session/**`, `app/api/focus-sessions/**`
(이번엔 `features/start-focus-session/**`가 scope에 포함되어 블로커 1/3을 직접 해결함).

### 받은 스펙 요약

1. `elapsedSeconds`를 "미션 전체 기간 누적"이 아니라 "오늘(자정 기준) 하루 집중시간
   합산"으로 되돌림 — 미션은 하루 단위 개념. 새벽 2시 컷오프는 별도 티켓으로 미룸.
2. 블로커 3 해결: `useStartFocusSession`과 `useUpdateFocusSession`을 하나로 통합하고,
   `MissionItem`의 "집중 시작" 버튼도 통합된 훅을 쓰게 해서, A를 일시정지한 채 B를
   시작해도 A가 일시정지 시점까지만 기록되고 마감되도록 함.

### 1. 오늘 범위 복원

`app/api/focus-sessions/route.ts`의 `fetchCurrentSession`(직전 변경에서 전체 기간 조회로
바꿨던 것)을 `fetchTodaySession`으로 되돌리고 `getTodayRange()`(`entities/focus-session/model/dateRange.ts`,
UTC 자정 기준)로 다시 필터링함. `mapFocusSessionRow.ts` 주석도 "전체 기간"→"오늘(자정~자정)"으로
수정. `closeOpenSession`의 "열린 세그먼트 찾기" 쿼리는 원래도 날짜 필터가 없었고 지금도
없음 — 자정을 넘겨 계속 열려 있는 세그먼트도 정상적으로 찾아서 닫아야 하므로 의도적으로
유지함(표시되는 합계만 오늘 범위로 자름).

`Mission.actualFocusMinutes`(미션 목록에 보이는 "· N분", `entities/mission/model/mapMissionRow.ts`
/ `app/api/missions/route.ts`)는 여전히 전체 기간 합산이라 이 타이머 위젯의 "오늘" 합계와
개념이 달라짐 — 이 두 파일은 이번에도 scope 밖이라 손대지 않음(아래 블로커 5).

### 2. 훅 통합 + 일시정지 중 다른 미션 시작 문제 해결

`features/start-focus-session/model/useStartFocusSession.ts`(scope에 새로 포함됨)를
`entities/focus-session/model/useUpdateFocusSession.ts`가 하던 일을 흡수하도록 다시 씀 —
`{missionId?, action: start|resume|stop, endedAt?}` 계약으로 확장하고, `stop`을 `stopped`로
로컬 덮어쓰던 옛 로직(더 이상 필요 없음, 서버가 이미 `idle`을 정확히 반환)을 제거함.
`useUpdateFocusSession.ts`는 삭제.

다만 "일시정지 중임"과 "일시정지 시점"은 여전히 `FocusTimerPanel`의 로컬 상태로만
존재하는데, `MissionItem`의 "집중 시작" 버튼(정확히는 그 클릭을 처리하는
`widgets/MissionBoard.tsx`)은 scope 밖이라 손댈 수 없고, `FocusTimerPanel`이 알고 있는
"일시정지 시점"을 그 버튼 핸들러에 전달할 방법이 없음. 그래서 "일시정지 시점"을
컴포넌트 로컬 상태가 아니라 **React Query 캐시에 전역 상태처럼 공유**하기로 함
(`entities/focus-session/model/pausedMarker.ts`, 신규): `usePausedMarker()`(읽기)/
`useSetPausedMarker()`(쓰기)로 `{missionId, pausedAt}`을 저장. `FocusTimerPanel.pause()`가
이 마커를 세팅하고, 통합된 `useStartFocusSession`의 `mutationFn`이 매 요청마다 "호출부가
`endedAt`을 안 넘겼는데 아직 안 지워진 마커가 있으면 그 시점을 대신 써서" 보냄:

```
const pending = queryClient.getQueryData(pausedMarkerQueryKey);
const endedAt = input.endedAt ?? pending?.pausedAt;
```

이렇게 하면 `MissionBoard.tsx`(scope 밖, 파일 수정 없음)가 여전히 `endedAt` 없이
`{missionId: B, action: "start"}`만 보내도, 마커가 살아있는 한 서버는 A의 열린 세그먼트를
"지금"이 아니라 A를 일시정지한 시점으로 닫음 — 파일을 하나도 건드리지 않고 `MissionBoard`/
`MissionItem`의 동작이 고쳐짐. 마커는 모든 성공한 요청의 `onSuccess`에서 무조건
지움(`setQueryData(pausedMarkerQueryKey, null)`).

`FocusTimerPanel`의 "로컬이 일시정지 중이면 서버 refetch를 무시한다" 동기화 가드도
같이 손봄: 예전엔 `status === "paused"`면 무조건 서버 값을 무시했는데, 이제는 마커가
아직 남아있을 때만 무시하고(`status === "paused" && pausedMarker !== null`), B가 시작되어
마커가 지워지면 곧바로 서버의 새 세션(B)으로 동기화하도록 바꿈 — 안 그러면 A가
정상적으로 마감된 뒤에도 화면엔 계속 A의 "일시정지" 화면이 남아있게 됨.
